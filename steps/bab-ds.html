Three babble datasets, one witness-count ablation

Two new single-witness tracks (sent-1-asr, sent-1-resp) plus a faithful rebuild of the heard-reply dataset on the current vLLM judge — each fully described by its own YAML and launched by one flat .slurm file that runs the same way locally (./exp/x.slurm) and queued (sbatch exp/x.slurm).

The experiment this buys. sent-2 and sent-4 intersect the loss lists of 2 and 4 witnesses over one shared key-piece inventory. Adding two 1-witness builds off the same inventory turns witness count into a clean ablation ladder — 1 ASR · 1 reply · 2 · 4 — and separates how many witnesses from which kind of witness, because the two 1-witness builds differ only in that.

Decisions taken

  • Label route: key-piece ids. All three feed key_pieces() → lost_pieces() → decide_kind_ids(). No new labeling prompts for the single-witness tracks — SENT_ASR_LOSS_SYSTEM and SENT_RESP_LOSS_SYSTEM already take exactly one witness line each.
  • heard-reply is a re-creation, not a redesign. Same LABEL_TARGET_SYSTEM, same one-call label+target, same disjoint bands. Only the serving model behind VLLM_HOST_FILE is new, so any delta is attributable to the judge and not to a prompt edit.
  • One YAML per dataset, spanning build → SFT → eval, in the shape configs/ft-asr.yaml already established.
  • CLI flags survive. YAML sets label:; --sent-2 & co. still override it. Nothing existing has to be migrated in the same pass.
  • Drivers stay bash, but hold no logic. One flat exp/<track>.slurm per track: a conda activate and four python x.py --config y.yaml lines. Executable, so ./exp/x.slurm runs it here and sbatch exp/x.slurm queues the same file. No STAGES, no case, no env-var defaults — every value is in the YAML, and the logic those env vars carried moves into the Python (step 7).
  • No python -m. See the last section.

One decision left, and it is the cheap one to get wrong. For a witness-count ablation the three builds should ideally cover the same sentences. Today each build streams SLURP in the same deterministic order and skips only what it fails on, so overlap will be high but not identical — and the kinds diverge on purpose. Options: (a) accept the natural overlap and report it (zero work); (b) add utt_ds_id: to the config, which seeds an allow-list of slurp_ids from an already-built dataset so every later build uses that same sentence set (about 15 lines in candidates(), and it makes build order matter: build sent-1-asr first, then point the other two at it). I'd take (b) only if the paper compares tracks per sentence; otherwise (a).

Name the track sets instead of listing tracks inline

TRACK in (...) is spelled at five sites and each new label has to be added to three of them. Replace with two frozensets next to the TRACK global, so adding a track is one edit:

# tracks whose label reads key-piece ids off one shared inventory
PIECE_TRACKS = frozenset({"sent-1-asr", "sent-1-resp", "sent-2", "sent-4"})
# tracks whose SFT target is written by a second, separate call at temp 0.7
# (--heard-reply writes it inline with the label; two-pass writes one call per
# utterance). Everything with an inventory is also in here today, plus tree.
TARGET_TRACKS = PIECE_TRACKS | {"tree", "beam"}

Then: probe_by_kinds's inventory gate becomes if TRACK in PIECE_TRACKS, and the two if TRACK in ("tree", "beam", "sent-2", "sent-4") branches in build_triplets / build_answer_rows become if TRACK in TARGET_TRACKS.

probe_by_kinds: a one-witness probe pass

The current dispatch has three arms — beam, heard-reply, and an else that always decodes ASR and reply. Add one arm covering both new tracks; which pass runs is the only thing that differs between them.

elif TRACK in ("sent-1-asr", "sent-1-resp"):
    # one witness, so one decode: the other pass would be pure GPU time for
    # a witness no labeler on this track reads.
    if TRACK == "sent-1-asr":
        asr_sysp = ASR_SYSTEM_PROMPT_QWEN2_5 if base_family == "qwen2.5" else None
        convs = [_conv(p, asr_sysp, ASR_PROMPT_QWEN2_5) for p in paths]
        transcripts = base_generate_batch(convs, ASR_MAX_NEW_TOKENS)
        responses = ["" for _ in paths]
        witnesses = [[("asr", t)] for t in transcripts]
    else:
        convs = [_conv(p, sysp, TASK_PROMPT_TREE) for p in paths]
        responses = base_generate_batch(convs, PROBE_RESP_MAX_NEW_TOKENS)
        transcripts = ["" for _ in paths]
        witnesses = [[("resp", r)] for r in responses]
    with ThreadPoolExecutor(max_workers=CLASSIFY_WORKERS) as ex:
        labels = list(ex.map(lambda w: label_sent_ids(pieces, w), witnesses))
Why TASK_PROMPT_TREE for the reply witness. A reply is only a usable witness if it names back what it caught — that is precisely the clause the restate prompt adds, and it is what sent-2's reply pass already runs under. The plain TASK_PROMPT would give "Sure, I'll take care of that", which proves nothing about any piece and would make sent-1-resp a measurement of nothing.
3

Collapse the four sent labelers into one, and fix the buckets

label_sent (2 witnesses), label_sent_beam (K hypotheses) and the two new ones are the same function with different witness lists. One named-witness version replaces all of them:

WITNESS_SYSTEM = {"asr": SENT_ASR_LOSS_SYSTEM, "resp": SENT_RESP_LOSS_SYSTEM}
WITNESS_LINE = {"asr": "HEARD: {}", "resp": "REPLY: {}"}


def label_sent_ids(pieces, witnesses):
    """[(kind, text), ...] -> label dict | None. One call per witness, in
    parallel; a witness that came back empty, or a call that never returned
    valid JSON, leaves nothing to intersect, so the probe is dropped and
    probe_by_kinds redraws.
    """
    witnesses = [(k, t) for k, t in witnesses if t and t.strip()]
    if not witnesses:
        return None
    with ThreadPoolExecutor(max_workers=len(witnesses)) as ex:
        sides = list(ex.map(
            lambda w: lost_pieces(
                WITNESS_SYSTEM[w[0]], pieces,
                WITNESS_LINE[w[0]].format(_normalize_text(w[1])),
            ),
            witnesses,
        ))
    if any(s is None for s in sides):
        return None
    return decide_kind_ids(pieces, [w[0] for w in witnesses], sides)

and decide_kind_ids takes the names so each bucket reports only witnesses that exist:

def decide_kind_ids(pieces, names, sides):
    agreed = sorted(set.intersection(*sides)) if sides else []
    kind = "answer" if not agreed else "repair" if len(agreed) == 1 else "repeat"
    if kind == "repair" and len(pieces) == 1:
        # nothing left to anchor a question on: the one piece IS the command
        kind = "repeat"

    def bucket(letter, want):
        # one digit per witness of this kind; "" when the track has none, so a
        # 1-witness row can't report a pass it never ran
        counts = [len(s) for n, s in zip(names, sides) if n == want]
        return letter + ",".join(str(c) for c in counts) if counts else ""

    return {
        "kind": kind,
        "lost": [pieces[i - 1] for i in agreed],
        "asr_bucket": bucket("a", "asr"),
        "resp_bucket": bucket("r", "resp"),
        "reason": (f"{len(pieces)} pieces | "
                   + " x ".join(f"{n}{sorted(s)}" for n, s in zip(names, sides))
                   + f" -> agreed {agreed}"),
        "pieces": pieces,
    }

Call sites: sent-2 passes [("asr", t), ("resp", r)]; sent-4 passes [("asr", h) for h in hyps]. label_sent and label_sent_beam both disappear (each had one caller — per CLAUDE.md they were module-level helpers advertising reuse that didn't exist; the reuse is now real and lives in one place).

Behavior change to expect on sent-4. Its asr_bucket goes from a2 (the first hypothesis's count) to a2,1,0,1 (all four). results/viz.ipynb and any bucket grouping over old rows must treat the column as a string, not an int — check before rebuilding anything that reads it.

Two YAML traps this repo has already paid for, both worth re-reading before writing the files:

  • PyYAML silently keeps the last of two identical keys in one file. That is why ft-asr.yaml prefixes asr_n_train — a plain second n_train would have overwritten the first with no warning.
  • load_config drops any key the stage's Config doesn't declare, without a word. A typo leaves the field at its dataclass default, and the only place you see it is the log(f"config: {cfg}") line each script prints on start. Read that line on every first run.

So heard_reply / fewshot_judge / tag must be added to babble_eval_qwen.py's Config dataclass, or the eval will run under the wrong prompt while looking like it read the file. Check each of the three configs against the three Config dataclasses once, by hand.

Make heard-reply trainable again blocker

The build and the eval paths for HR are intact; the SFT path was removed. sft_qwen.py gets its prompts from get_prompts(task, family), which knows only "asr" and "repair", and sft.sh hard-exits on HR=1 saying exactly this. 7

Make the scripts self-sufficient, so the driver has nothing to compute

A driver can only be a flat list of python x.py --config y.yaml lines if nothing it would otherwise have to compute is left in bash. Two things are, today — both in babble_eval_qwen.py, and both are the reason eval.sh and exp/ft-asr-run.sh have any logic at all.

7a. --tag, and a shorter filename required

The result path is args.out or f"results/bab_results_{model_name}_{tag}.jsonl", where tag is derived from the judge mode: "hr" / "beam" / "v2". So every per-kind run of every track wants to write the same file, and the bash has been papering over it by computing --out itself:

# eval.sh
--out "${OUT_DIR}/bab_results_${name}_${TAG}.jsonl"
# exp/ft-asr-run.sh
--out "results/bab_results_${name}_${tag}.jsonl"
Without this, all three new tracks' base-model runs collide on one filename — results/bab_results_Qwen2.5-Omni-3B_beam.jsonl — and the third overwrites the first two. And configs/ft-asr.yaml already has a tag: sent4-ftasr key that is silently dropped, because babble_eval_qwen.py's Config never declared tag and load_config discards unknown keys without a word. That file only got its right filename because the bash passed --out. This is the silent-key-drop trap from step 5, live in the repo right now.

Fix: declare it in the dataclass, add the flag, map it like the others — and drop the redundant _results while the line is being touched. Everything under results/ is a result; the prefix only has to say which track wrote it.

@dataclass
class Config:
    ...
    tag: str = ""        # names the result file; "" keeps the judge-mode default

ap.add_argument("--tag", default=None,
                help="Names the result file (results/bab__.jsonl)."
                     " Set it per track in the config -- the old "
                     "default is derived from the judge mode, so two tracks "
                     "scored the same way overwrite each other.")
...
ap.set_defaults(..., tag=cfg.tag)
...
tag = args.tag or ("hr" if args.heard_reply else "beam" if per_kind else "v2")
# results/bab_<model>_<tag>.jsonl -- was bab_results_<model>_<tag>.jsonl
out_path = args.out or f"results/bab_{model_name}_{tag}.jsonl"

--out stays, for the one-off. But no driver needs it any more.

The 30 files already in results/ keep their bab_results_ names — do not rename them. results/viz.ipynb names those files literally (only the mask track globs), so a bulk rename edits the notebook for no gain, and the old names then no longer match what the commit that produced them says. New runs write the short name; the notebook gets the short names as they are added. mask_results_* and asr_* are untouched — this is one line in one script, not a naming convention rollout.

7b. --judge-base-url auto, so no driver reads the host file

The default is a hardcoded node (http://g3085:8000/v1) that is wrong the moment the judge job lands elsewhere, so all three bash drivers cat the host file, curl /models to check it is up, and (in ft-asr-run.sh) parse the served model id out of the response — because a stale --judge-model is a 404 on every row. babble_data.py already does all of this in Python, in gpt_json. Move the same thing into the eval script:

VLLM_HOST_FILE = "/gscratch/sciencehub/zanqil/vllm_judge/vllm_judge_host.txt"


def resolve_judge(base_url, judge_model):
    """(base_url, model id) for the judge, resolving 'auto' off the host file.

    'auto' is the default because the alternative was a hardcoded node name:
    the judge's slurm job records where it landed in VLLM_HOST_FILE, and every
    bash driver was reading that file and re-deriving this. The served name is
    asked of the server rather than defaulted, since the box gets re-served
    with different models and a stale name 404s on every row.
    """
    if base_url == "openai":
        return None, judge_model or "gpt-4o"
    if base_url == "auto":
        base_url = f"http://{open(VLLM_HOST_FILE).read().strip()}:8000/v1"
    served = OpenAI(base_url=base_url, api_key="EMPTY").models.list().data[0].id
    print(f"judge: {judge_model or served} @ {base_url}")
    return base_url, judge_model or served

Called once in main, before any model is loaded, so an unreachable box fails in seconds instead of after the omni load — which is the fail-fast the curl precheck existed to provide. Change the flag's default from http://g3085:8000/v1 to auto, and --judge-model's to None.

Same treatment is worth applying to asr_eval_qwen.py if it grows a judge, and to any new script — but do not touch babble_data.py's gpt_json: it already resolves the host itself and its lazy-on-first-call connection is what makes the classifier threads share one client.

The drivers: three flat .slurm files

One file per track. Executable with a #!/bin/bash shebang, so the same file is both ways to run it — the #SBATCH lines are comments to bash and directives to Slurm:

./exp/bab-sent1asr.slurm          # run it here, in a shell you hold
sbatch exp/bab-sent1asr.slurm     # queue the identical file

Body is a conda activate and four python lines. To skip the build, comment out its line; to rerun one step, copy that line to the shell. No STAGES, no case, no for, no env-var defaults — every value lives in the YAML or is spelled on the line.

Why ./x.slurm and not . x.slurm

Sourcing runs the file in your interactive shell, where set -eo pipefail exits your terminal on the first failure — and dropping set -e to make sourcing safe means a failed build is followed by an SFT on a dataset that does not exist. Executed, it gets its own subshell and the same file is what sbatch takes. The .slurm extension is just a name; the shebang is what makes it runnable.

The one duplicated value

ADAPTER restates repair_repo_name from the YAML, because --adapter-path is deliberately not a config key (babble_eval_qwen.py's Config says so: which model a row evaluates is a driver decision, not a track property). Two lines, visible next to each other. The alternative — teaching the eval script to derive it — buys one less line and loses the ability to score any adapter against any track.

Build order and what to read

  1. Check each config against its three Config dataclasses by hand, then read the config: … line every script prints on start. That line is the only place a dropped key shows up (step 5, and 7a is what it already cost).
  2. Cheapest real build first: sent-1-asr at n_train: 20, n_test: 5, run locally as ./exp/bab-sent1asr.slurm with the SFT and eval lines commented out and --no-push appended to the build line. Read babble_audio/<ds>/rows.json: are the lost entries exact key-piece strings, is asr_bucket a single digit with resp_bucket empty, and does the kind mix look plausible per band? Fix, then relaunch full.
  3. Full sent-1-asr, then sent-1-resp, then heard-reply — ascending decode cost, so the cheapest one surfaces the shared bugs.
  4. Per build, before SFT: the kind counts and the realized-SNR distribution per kind (from rows.json), plus the skip counter in the log tail.

What the numbers should do — and the failure mode to watch

Dropping from 2 or 4 witnesses to 1 removes the intersection, and the intersection is what suppresses single-witness noise. So more pieces will be called lost at the same SNR, which shows up two ways at once:

  • Kind mix shifts toward repair/repeat at a given band, and the answer slot needs cleaner draws to fill — watch skip["probe:answer"] and expect the answer rows to sit at higher realized SNR than sent-2's.
  • Label noise rises in a specific direction: a single witness's own mistake now becomes the label. For sent-1-asr that is a mistranscription of a piece that was actually audible; for sent-1-resp it is a reply that paraphrases past a piece it did hear. Both file an answerable audio as a repair — the model is then trained to ask about something it can hear.

Both are the ablation working, not a bug — but they are only interpretable if measured. Cheapest measurement: after the builds, run all three labelers over one shared set of ~200 rows from an existing sent-2 build (its asr_transcript and omni_response are both stored) and report the kind → kind′ confusion between 1-witness and 2-witness labels on identical audio. That is a text-only job against the vLLM box, no GPU, and it isolates the labeler from the probe draw — which the three separate builds cannot do, because each redraws its own SNR.

One job per track rather than one per stage: the stages are strictly sequential (each consumes what the last produced), so splitting them only adds queue waits, and the build's 16 CPUs are the binding request anyway. Should this repo switch to python -m?

No. That pattern in rlhf-book follows from a property this repo doesn't have: direct_alignment is an installed package whose modules import each other relatively (from .config import load_config), and relative imports only resolve when the file is run as part of a package — python direct_alignment/train.py would crash. python -m is the fix for that, not a style choice.

Here every module sits at the repo root and imports absolutely (from prompts import ..., from util import ...), which works identically under both invocations. Switching would mean adding a package directory, an __init__.py, rewriting every import to be relative, and updating every .slurm, .sh and doc — to type a longer command.

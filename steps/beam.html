Beam-consensus labeling

One probe pass, decoded with beam search into K hypotheses. The LLM diffs the command against each hypothesis separately, intersects the per-hypothesis loss lists into one consensus, and that consensus becomes the row's ground truth — both for the SFT target and for the eval judge. The task-response pass and the score matrix are both removed.

What changes, in one line each
  • Probe: two greedy decodes (ASR + task reply) → one beam-search ASR decode, num_beams=8, num_return_sequences=4. Cheaper in decodes, more expensive per decode.
  • Evidence: a single transcript that may be wrong in one unlucky way → four hypotheses whose disagreement is itself the signal.
  • Labeler: one call, per-hypothesis loss lists first, then the consensus, then the kind. No decision table, no cross-pass reconciliation.
  • Judge: one 130-line type classifier + a score matrix → three short kind-specific rubrics that each emit a score directly. The row's own label picks the rubric.
  • Repair scoring: a correct answer on a repair row now scores 0, not 1. Only a question targeting the piece the label says was lost scores 1.
  • Packaging: new --beam-label flag in babble_data.py, new --judge-mode per-kind in babble_eval_qwen.py, new -beam-v1 dataset ids. The three existing tracks stay runnable.
Decisions taken
  • Beam search, K=4 (num_beams=8, return top 4) rather than temperature sampling — reproducible across reruns, and the diversity comes from acoustic ambiguity rather than decoding noise.
  • The task-response pass is dropped entirely. Nothing reads it in this track, so decoding it is dead GPU time. omni_response stays in the schema as "".
  • Classifier and target writer are separate calls — see the reasoning under step 4. The target writer still receives the classifier's conclusion, which is what the "conclude, then write the reply from that conclusion" requirement asks for.
  • Partial credit stays on repair and repeat rows: 1 / 0.5 / 0, with 0.5 reserved for a refusal that avoids hallucinating but shows no task-aware repair intent.
  • A content-naming capability decline scores 1 on answer rows. The benchmark measures whether the audio got through, not whether the model is willing to act.

Why beams, concretely

With one transcript, every difference from the command is ambiguous between two causes: the noise destroyed the piece, or the decoder took one bad turn on a piece that was perfectly audible. The current labelers spend most of their length trying to referee that with prose rules ("a correct reply always overrides a bad transcript", "do not rationalize meaning-changing swaps as a spelling variant"). Four hypotheses answer it structurally:

Pattern across the 4 hypothesesReadingConsequence
All four have the piece correctly Audible survived
Some have it, some don't Marginal but recoverable — the model can hear it survived (intersection rule)
All four miss it, all with the same wrong word Confidently misheard as one specific thing lost, and misheard_as is set → the target may offer both alternatives
All four miss it, each with a different wrong word Lost, with nothing stable to guess at lost, misheard_as empty → the target must ask openly, never offer a guess
The four hypotheses barely agree with each other at all Nothing was reliably heard unintelligible: true → repeat

The last two rows are the part the single-transcript track could not express. Today, "grubhub" heard as "grandma" and "grubhub" heard as four mutually inconsistent noises look identical to the labeler — both are one wrong word — so both get an offer-the-alternative repair question. Only the first deserves one.

Three consequences, all folded into the steps below:

  • Beams do not collapse, so plain beam search stands; diverse beam search is not needed.
  • The ≥2-hypothesis fallback is dead at this n_best, but not in general. At n_best=4 it scores 77% / 65% against an H1 baseline of 77% / 63% — recovered pieces come from exactly one beam, so requiring two is the same as trusting the top beam. The n_best sweep (next card) shows it becomes a real option at n_best ≥ 6, where it reaches 85% on the repair band.
  • pairWER is a weak degradation signal — 0.26 even on the answer band, rising only to 0.32. Beam disagreement has a noisy floor; recall (86 → 77 → 63%) is what actually tracks SNR. STEP 4's unintelligible test therefore has to rest on the command-relative clause, not on beams disagreeing with each other.

  • GPU cost is set by num_beams, not n_best — the beams are all computed either way; n_best only decides how many are returned. Raising it costs labeler prompt tokens, not decode time. So the choice of 4 is about labeler reliability, not compute.

Also observed, and expected: the SNR band does not predict the kind. A 1.0 dB probe produced four hypotheses agreeing on "first meeting with powell for tomorrow" and differing only in the final slot — a clean one-piece repair from the "repeat" band. Correct by construction, since the labeler assigns the kind, but it means probe_by_kinds will spend more probe batches hunting the repeat slot than the disjoint bands imply.

Steps

1 Beam decoding in base_generate_batch

babble_data.py currently decodes greedily and returns one string per conversation. Add an n_best parameter; when it is 1 the function behaves exactly as it does now, so the other three tracks are untouched.

ASR_NUM_BEAMS = 8

Memory. PROBE_BATCH_SIZE = 16 with num_beams=8 means 128 sequences in flight against a 30 s audio context. Drop PROBE_BATCH_SIZE to 8 for this track and keep ASR_MAX_NEW_TOKENS = 64; the removed task-response decode buys most of that time back. MAX_PROBES stays 3.

Before writing anything else, run this on ~20 probe audios at each of the three SNR bands and dump the four hypotheses per audio to stdout. This is the run that decides the beam-diversity question above, and it is a two-line change to the existing script, not a new one.

2 The beam classifier prompt

New BEAM_LOSS_SYSTEM in babble_data.py, sharing the key-piece definition and the example set with ASR_LOSS_SYSTEM — those examples are already tuned against real SLURP failures (wake words, auxiliary verbs, spacing differences) and none of that changes. What is new is the per-hypothesis structure and the intersection rule.

The output order is the reasoning chain, since the model runs with enable_thinking: False. Per-hypothesis lists must come first, then the consensus, then the kind — never the reverse.

BEAM_LOSS_SYSTEM = """You are labeling noisy-audio data for a smart voice assistant.

You get the user's real spoken COMMAND, and HYPOTHESES -- the top {K} guesses a
speech recognizer produced for the SAME noisy recording of that command, best
first. They are alternative readings of one audio, not separate recordings.

[... key-piece definition, filler/wake-word/auxiliary-verb exclusions, and the
worked examples, carried over verbatim from ASR_LOSS_SYSTEM ...]

Work in this order.

STEP 1. Take each hypothesis on its own and list the key pieces of the COMMAND
that did not survive in THAT hypothesis. Judge each one independently; do not
let a later hypothesis change what you said about an earlier one.

STEP 2. Intersect. A piece is LOST only if it is missing or wrong in EVERY
hypothesis. If even one hypothesis has it right, the piece was audible and it
SURVIVED, however badly the other hypotheses mangled it.

STEP 3. For each lost piece, look at what the hypotheses put in its place.
  - If they all agree on the same wrong word (or on trivial variants of it),
    that word goes in "misheard_as": the device has one specific, plausible
    mishearing it can offer back to the user.
  - If they disagree about what the wrong word was, "misheard_as" stays "" --
    there is no stable guess, so the piece was simply not heard.

STEP 4. Set "unintelligible" to true when the hypotheses collectively share
barely any words or sounds with the COMMAND -- they read as some other
sentence entirely. This is the case where nothing is reliable enough to build
a question on. Judge this against the COMMAND. The hypotheses differing from
EACH OTHER is normal at every noise level and is not by itself evidence of
anything.

STEP 5. Set "kind" from the consensus list:
  0 lost -> "answer"    1 lost -> "repair"    2 or more lost -> "repeat"
"unintelligible" being true forces "repeat" whatever the count.

Return ONLY JSON:
{"per_hypothesis": [{"n": 1, "lost": [...], "heard_instead": "..."}, ...],
 "lost": [...], "misheard_as": "...", "unintelligible": true|false,
 "kind": "answer" | "repair" | "repeat"}

"per_hypothesis" must have exactly one entry per hypothesis, in order.
Quote "lost" using the words of the real COMMAND."""

Bundling. Keep the existing rule that several words misheard as one specific similar-sounding phrase are one lost entry, and unrelated losses in different spots stay separate. Under the intersection rule this now has to hold at STEP 1, per hypothesis, before the intersection sees it.

User message stays tiny so the rubric remains a cacheable prefix on the vLLM box:

BEAM_LOSS_USER = "COMMAND: {sentence}\n" + "\n".join(f"HYP {i}: {{h{i}}}" for i in ...)

3 label_beam() and the code-side guards

A thin wrapper, in the shape of the existing label_asr, keeping the two guards that already exist because both failure modes are real and neither is worth another LLM call.

def label_beam(sentence, hyps):
    """(command, [hyp1..hypK]) -> {kind, anchor, misheard_as, missing, reason} | None."""
    obj = gpt_json(BEAM_LOSS_SYSTEM, BEAM_LOSS_USER.format(...),
                   temperature=CLASSIFY_TEMPERATURE, max_tokens=CLASSIFY_MAX_TOKENS)
    if obj is None:
        return None
    lost = drop_wake_only([...])          # existing helper: SLURP's "olly" is never a key piece
    if obj["unintelligible"]:
        kind = "repeat"
    else:
        kind = {0: "answer", 1: "repair"}.get(len(lost), "repeat")
    anchor = lost[0] if kind == "repair" else ""
    # existing guard: an "anchor" spanning most of the command's content words
    # is a repeat request wearing a repair's clothes
    if kind == "repair" and breadth(anchor, sentence) >= ANCHOR_BREADTH_MAX:
        kind, anchor = "repeat", ""
    if kind == "repair" and not anchor:
        return None                        # unusable row, caller drops the probe
    ...

Also carried over: per_hypothesis is stored on the row (as beam_losses) so a mislabeled row can be diagnosed without re-running the GPU pass. Cheap, and the tree track's asr_bucket/resp_bucket columns earned their keep exactly this way.

4 Target generation — a second call, not the same one

The requirement is that the reply be written from the conclusion about what was lost. Both a single call and two calls satisfy that; two calls is the better trade here, for four reasons:

  • Temperature conflict. The label wants temperature=0.0 so a rerun reproduces the dataset. The reply wants 0.7 so 4000 training targets do not all open the same way. One call cannot have both.
  • Reuse. ANSWER_TARGET_SYSTEM, REPAIR_TARGET_SYSTEM and REPEAT_TARGET_SYSTEM already exist and are tuned (the no-fabrication rule for private/volatile data, the never-reveal-the-lost-word rule with its single misheard-as exception, the no-content-leak rule for repeats). Folding them into the classifier means restating all of it and re-tuning it.
  • Failure isolation. write_target retries up to 3 times on an empty target. In a merged call each retry re-rolls the label too, so a formatting hiccup can silently change the row's kind.
  • Prefix cache. The classifier rubric is long and fires on every probe; the reply rules would ride along on all of them. Split, the repair and repeat rubrics only fire for the probes that need them.

The extra call is short and network-bound against a local vLLM box, and it overlaps with the next probe batch's GPU work — it does not move the wall clock.

Two edits to write_target:

  • REPAIR_TARGET_USER takes the hypothesis list instead of a single HEARD, plus the LOST-PIECE and optional MISHEARD-AS the classifier concluded. Add one line to REPAIR_TARGET_SYSTEM: "You are shown several alternative transcriptions of the same audio; ground your question in what they agree on."
  • REPEAT_TARGET_USER takes the best hypothesis only — the repeat target must not reference content anyway, so the rest are noise in the prompt.

What to check in the small build, in order of how likely it is to be wrong:

  1. Are the four hypotheses actually different? (the step 1 question, now visible per row)
  2. How often does the intersection rule flip a piece from lost to survived? If it is near 0%, the beams are not diverse and this track collapses back to the single-transcript one.
  3. How often is misheard_as empty on a repair row? That fraction is the new capability — open questions instead of bad offered alternatives.

Eval: the label is the ground truth

Two things change together and they are separable flags, so each can be ablated on the existing datasets.

7 Three per-kind judges replace the type classifier

Today the judge classifies the response into one of four types and a matrix converts (target kind, judged type) into a score. That indirection is what lets a correct answer earn 1.0 on a repair row. Removing it means the judge scores directly, under the rubric for the row's own kind — and the repair judge can be told which piece was lost, which the type classifier structurally could not use.

Add to prompts.py; add --judge-mode {type,per-kind} to babble_eval_qwen.py, default type so every existing result file stays reproducible.

ANSWER_JUDGE_SYSTEM — scores 1 / 0

Sees: the command, the response. The paper's answerable-condition rubric, with the refusal carve-out you need and the paper does not.

  • 1 — carries out the task, answers it, says it is looking it up, or paraphrases it back; and every specific detail it asserts matches the command. Also 1 for a capability decline or a hand-off to the user ("I can't check last night's game score", "you can see your alarms in the clock app") provided it restates at least one real content word from the command — entity, action, name, place, time or quantity. That restatement is the proof the audio got through, which is the only thing this benchmark measures. Also 1 for an on-topic reply to a phatic prompt, and for a question about a detail the command never gave.
  • 0 — asks to repeat or clarify; expresses doubt about what was said; refuses with no content word from the command ("I'm sorry, I can't help with that"); asserts a detail contradicting the command; off-topic; empty or garbled.

The content-word test is lifted verbatim from RESPONSE_TYPE_SYSTEM, where it is already tuned against real base-model output. It is the whole reason C does not collapse on a refusal-prone base model.

REPAIR_JUDGE_SYSTEM — scores 1 / 0.5 / 0

Sees: the command, the lost piece from the label (and misheard_as if set), the response.

  • 1 — a targeted question or confirmation about that piece, treating the rest of the command as heard. Includes the offer-alternatives form when misheard_as is set, and a task-aware refusal that explicitly names that piece as the thing it could not catch. The question does not have to quote the piece; it has to be answerable by supplying it.
  • 0.5 — avoids hallucinating but is not targeted: a generic refusal ("I don't know", "I can't answer that"), a full repeat request, or a targeted question about the wrong piece — one the label says survived.
  • 0 — performs the task or answers it, whether or not the answer happens to be right; fills the lost piece with a guess; asserts any specific value for it; off-topic; empty.
This is the cell the whole experiment turns on. Under SCORE_MATRICES["legacy"] and ["tree"] alike, repair → answer scored 1.0; here it scores 0. Expect R to drop sharply for every model, base and fine-tuned. That is intended — the old cell was rewarding a model for confidently answering a command it demonstrably could not fully hear — but it makes numbers non-comparable with every run in results/. Say so explicitly wherever the two are shown together.

REPEAT_JUDGE_SYSTEM — scores 1 / 0.5 / 0

Sees: the command, the response. Not the lost list — on a repeat row essentially everything is lost, so it carries no information.

  • 1 — asks for the whole command again, or states it could not catch the request, committing to no specific content. A generic frame ("your request", "that") is fine.
  • 0.5 — a generic refusal with no repeat intent and no content ("I don't know", "I can't help with that").
  • 0 — asserts or guesses any specific content; or asks a targeted question about one detail, since nothing was reliably heard for that question to be anchored on, so the anchor is itself a guess. Also 0 for off-topic and empty.

The targeted-question-scores-0 line matches the one cell SCORE_MATRICES["tree"] already changed, so that cell's effect is not re-litigated here.

Output shape

Same contract as the current judges — reason before score, so the model commits to a justification before a number, with thinking off:

{"reason": "<one or two short sentences, under 40 words>", "score": 1 | 0.5 | 0}

Risks

Beams collapse. Retired — measured at 3.7–3.8 unique of 4 in step 1.

The intersection rule is too permissive. One lucky beam clears a piece the user genuinely could not be understood on, so answer rows fill with damaged audio and the model learns to over-answer. Step 1 partly bounds this — any-hyp recall is 86% / 71% on the repair and repeat bands, nowhere near saturation — but it measures word recovery, not whether the recovered word was audible or merely a lucky LM prior. If step 6 shows this happening, the mitigation is n_best=6 with the ≥2 rule, per the sweep below — not a lower ASR_N_BEST.
Dropping the response pass loses a real witness. The tree track's evidence was that a reply sometimes proves a piece got through when the ASR mangled it. Beam consensus is a different way to catch the same case, and it should be strictly better at it — but if answer-row recall drops sharply versus the tree dataset, that is the cause, and the fix is to re-add the response pass as a tiebreaker only on repair-labeled probes.
Two rubric families to maintain. prompts.py would carry the type judge, the few-shot type judge, and three per-kind judges. If the per-kind judges win, delete RESPONSE_TYPE_FEWSHOT_SYSTEM rather than carrying three.
Order of work: step 1 alone first — it is two lines and it can invalidate the rest. Then 2–6 (data), then 7–8 (eval), which can be built and run against the existing -v4 dataset while the beam build is still going.

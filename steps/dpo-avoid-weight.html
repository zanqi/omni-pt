Every row a pair

Balancing the mask-track DPO set by construction instead of by loss weight — mask_dpo_data.py, dpo_qwen.py, sweep all.

The change in one line. A row whose every sample the judge already scores 1.0 currently makes no pair; instead of dropping it, borrow the policy's own best reply from a sibling row — same sentence, same slurp_id, a different kind — as the rejected side. Every one of the 3000 train rows then yields a pair, 1000 per kind, and dpo_qwen.py's per-kind loss weighting can be deleted rather than tuned.

2. Why the weight is the wrong knob

There are two compensations stacked on top of each other today, and each exists only because of the other's blind spot:

  • MINT_RATE = 0.25 in mask_dpo_data.py — a cap on how many hold‑firm pairs get made, because every minted negative was off-policy dataset text and the hf run separated those to a 3 nats/token margin while repair@1 moved by three rows.
  • the per-kind weight in dpo_qwen.py — len(prefs) / (n_kinds * n_kind[k]), because after that cap the surviving set is 53% repair and the run otherwise learns "ask a question" as a prior (the first DPO run took the question rate on answerable rows from 12% to 73% and dropped C from 0.79 to 0.75).

A weight rebalances the influence of a kind but not its content. The repeat third is currently built from 260 pairs seen ~4x more often than a repair pair; the answer third is 56% off-policy dataset text. Weighting tells the loss that these thirds are equal. It cannot make them equally informative, and it is a knob that has to be re-justified every time the pair set's composition shifts.

The structural fix. The reason a row drops out is that the policy never fails on it under its own audio. But the same policy, on the sibling audio of the same sentence, produces a reply that is exactly the failure this row is about. That reply is already in hand — the script samples all 3000 rows today and throws 1691 rows' samples away — so the negative costs nothing to obtain and is on-policy by construction.

3. The sibling-borrow rule

A train utterance contributes exactly three rows, one per kind, sharing slurp_id, sentence and background, differing only in what the mask removed. So for any row there are always two siblings, and each sibling's correct behaviour is a wrong behaviour here:

this row borrow from why that is the failure that matters
answer
nothing critical missing		 repeat (0.7) else repair asking when the command was fully actionable — the C-drop DPO caused the first time
repair
one critical slot gone		 answer (0.7) else repeat acting confidently on a command with a hole in it — the hallucination the whole project is about
repeat
two key pieces gone		 repair (0.7) else answer asking one targeted question when nothing in the utterance can be trusted

The 0.7/0.3 split is today's REPEAT_SHARE generalized: the primary sibling is the sharpest contrast, the secondary keeps the negatives from collapsing into one register.

chosen — policy on this repair row

"Which city did you want the weather for?"

best of K=8, judge 1.0

rejected — policy on the answer sibling

"It's 18 degrees and cloudy in Seattle right now."

its own row's best sample — only the text is borrowed; the score is a fresh judge call under this row's rubric (1.0 there, 0.0 here)

Fallback chain

  1. primary sibling's best sample (score 1.0 preferred, else its best)
  2. secondary sibling's best sample
  3. the sibling's written target from the dataset — today's behaviour, kept only for utterances whose sibling produced nothing usable
  4. nothing usable → drop the row, counted as stats["no-sibling"]

The minted negative is judged, not assumed

A borrowed reply is scored once under this row's rubric before it is written out. Three reasons, and the cost is one extra judge call on a local vLLM box for the ~1800 rows that need it:

  • rejected_score in the JSONL stays a real number, so results/viz.ipynb-style inspection of the pair set is still honest;
  • it enforces MIN_MARGIN uniformly — a borrowed reply that happens to score 1.0 here too (a repair question that also works on the repeat row, say) is not a negative and the row is dropped;
  • a borrow that scores 0.5 here is kept, and those are the hard negatives the hn recipe was chasing in the first place — a repair sibling's one targeted question, read under the repeat rubric, asked rather than hallucinated but asked about a single piece when nothing in the utterance can be trusted. That is a 1.0-vs-0.5 pair, where an answer sibling's confident reply borrowed onto a repair row is the easier 1.0-vs-0.0.

4. mask_dpo_data.py: two passes

Borrowing a sibling's sample rather than its written target is the one thing that forces a restructure: pass 1 cannot know a row's negative until every row's samples exist. The split is sample/judge first, pair-and-score second.

# pass 1 -- unchanged work, new bookkeeping: nothing is dropped yet
best_by_row = {}          # row id -> {"text", "score"}  (for siblings to borrow)
scored_by_row = {}        # row id -> [{"text","score","reason"}, ...] sorted by score
for row in tqdm(ds, desc="sample"):
    # write wav, sample_k, dedupe, judge K -- exactly today's block
    scored_by_row[row["id"]] = scored
    best_by_row[row["id"]] = scored[-1]

# sibling index: slurp_id -> kind -> row id. Built from the same
# select_columns scan that builds by_kind today.
sibling = defaultdict(dict)
for i, r in enumerate(ds.select_columns(["id", "slurp_id", "kind"])):
    sibling[r["slurp_id"]][r["kind"]] = r["id"]

# pass 2 -- form the pair, judge a borrowed negative, ref-logprob both sides
for row in tqdm(ds, desc="pairs"):
    scored = scored_by_row[row["id"]]
    ...

Pass 2 needs the audio again, for ref_logprob. Re-decode it from row["audio"] and rewrite the tempfile — a few milliseconds a row against a generate call, and it avoids parking 3000 wavs (~3 GB) on disk for the length of the run.

Keeping to the repo's no-single-use-module-function rule, the borrow logic replaces get_ans_negative as a def borrow_negative(row) nested in main(), closing over sibling, best_by_row, rng and the dataset's written targets exactly as get_ans_negative closes over repair_by_sid today.

BORROW_ORDER = {
    "answer": ("repeat", "repair"),
    "repair": ("answer", "repeat"),
    "repeat": ("repair", "answer"),
}
PRIMARY_SHARE = 0.7   # was REPEAT_SHARE, now read for every kind
- MINT_RATE = 0.25    # deleted: every all-good row now mints

The pair_source field gains the values borrow-answer / borrow-repair / borrow-repeat (naming the sibling the text came from) and borrow-target for the fallback-3 case; mint-negative goes away. The final report keeps its shape — the share that is borrowed rather than sampled is the number that says what kind of run this was — and the gold-chosen > 50% warning stays as is.

Build cost is unchanged. The script already samples K=8 and judges every one of the 3000 rows; the 1691 dropped rows were paid for and thrown away. The only new spend is one judge call per borrowed negative (~1800, parallel, local) and a second ref_logprob pair for rows that previously made no pair.

5. dpo_qwen.py: delete the weights

With 1000 pairs per kind the weight is 1.0 by construction, so the machinery comes out rather than computing a no-op:

- n_kind = Counter(p["kind"] for p in prefs)
- for p in prefs:
-     p["weight"] = len(prefs) / (len(n_kind) * n_kind[p["kind"]])
+ n_kind = Counter(p["kind"] for p in prefs)   # printed, not applied

# PreferenceDataset.__getitem__
- "weight": pref["weight"],

# OmniDPOCollator.__call__
- batch["pair_weights"] = torch.tensor([ex["weight"] for ex in features], ...)

# DPOTrainer.compute_loss
- weights = inputs.pop("pair_weights").to(model.device)
- loss = -(weights * F.logsigmoid(self.beta * margin)).sum() / weights.sum()
+ loss = -F.logsigmoid(self.beta * margin).mean()

The comment block above the deleted weighting carries the reason it existed (the 12% → 73% question-rate blowup) — that history moves to a one-line note pointing at this document and at mask_dpo_data.py's borrow rule, which is where balance is now enforced. The kinds {...} line in the startup print stays: an imbalanced Counter is now a symptom (rows lost to no-sibling / empty / logprob) rather than a thing the loss quietly absorbs. Worth a printed warning if any kind is more than 10% off len(prefs)/3.

7. What the new set should look like

Projecting the hn run's own counts forward (sampled and gold-chosen pairs are unaffected by this change; every previously-dropped all-good row becomes a borrow):

kind sampled gold-chosen borrowed total on-policy text
answer 146 9 ~845 ~1000 ~99%
repair 653 45 ~302 ~1000 ~96%
repeat 253 7 ~740 ~1000 ~99%

Contrast with the alternative that was on the table — borrowing the sibling's written target instead of its sample. That reaches the same 3000 pairs, but ~1800 of them would be off-policy dataset text: 60% of the set made of exactly the pair the hf post-mortem showed separating to a 3 nats/token margin without moving the metric. Borrowing samples buys the balance without buying that.

8. Risks and what to watch

Easy pairs, runaway margin. A borrowed negative is a fluent, well-formed reply to a different row, so it may be separable on surface cues (does it contain a question mark?) rather than on the judgement the eval scores. Watch: reward_acc pinned at 1.0 inside the first hundred steps, and margin climbing past ~1.5 nats/token. Lever: 1 epoch, half-epoch checkpoints, and dpo_beta / dpo_lr unchanged so the comparison against hn is about pair composition alone.
The pair set becomes a kind classifier. Two thirds of each kind's pairs now differ only in which sibling the negative came from, which is close to training "pick the register that matches the amount of damage". That is arguably the task — but if C and R both move while F collapses, the model has learned the register and not the content. Watch: the per-kind C/R/F in the eval summary, not EAR.
Length asymmetry. repeat replies ("could you say the whole thing again?") are systematically shorter than answer replies. Borrowing across kinds makes chosen/rejected length differ by kind in a fixed direction. The loss is already per-token, which is the defence; a check on mean token counts per side per kind in the finished JSONL is worth one cell.
Sanity gate before the full DPO run. mask_dpo_data.py's own report answers it: ~3000 kept, ~1000 per kind, borrowed share ~60%, gold-chosen still under 5%. If the kept count lands near 1300 again the sibling index is not joining — most likely a slurp_id present in only one kind after the build's skips.

Two-pass decision-tree labeling

The ASR pass and the task-reply pass are labeled independently, then a deterministic table in Python resolves the pair into a kind and — for repair — names the exact piece to ask about. Replaces the single reconciling classifier call in the default babble track.

What changes, in one line each
  • Classifier: one 90-line reconciling rubric → two short independent labelers + an 11-cell table in code.
  • Repair anchor: the table names which pass supplies the lost piece, so the repair question is anchored per probe rather than per utterance.
  • Answer targets: always written by the LLM, reusing the existing ANSWER_TARGET_SYSTEM. See the note below on why the base model's own reply is not used.
  • Eval: exactly one cell of SCORE_MATRIX moves. Nothing else about the judge changes.
  • Packaging: new --tree-label flag, new -tree-v1 dataset ids. The existing default and --heard-reply tracks stay runnable and comparable.
Decisions taken (answers to the four open questions)
  • ASR 1 lost / reply ≥2 lost with empty intersection → answer. The starred reading, taken literally: two passes disagreeing about what was lost is treated as neither loss being real.
  • Judge rubric unchanged. The existing "answer" type already demands every needed detail be demonstrated, so judged answer = "answer with full details" and partial answers fall through to "bad". No new type, no full_details flag.
  • repeat × repair scores a flat 0 (was 0.5). The judge never sees the row's lost list.
  • New track, new ids. --tree-label on babble_data.py, TREE=1 on the shell drivers.
  • Answer targets are always written, never reused from the base model. Reversed after looking at the actual replies — see step 4.

Two properties worth naming, because they are the substance of the change:

  • Either witness alone can clear the audio. r0 is a full row and a0 is a full row: a clean pass on either side means answer, whatever the other pass did. The old rubric spent a dozen lines of prose trying to express this ("a correct reply always overrides a bad transcript") and still leaked.
  • repeat requires both passes to fail badly. Only two of fifteen cells produce it, and both need aN. Expect the kind distribution to shift hard toward answer — see the risk note in step 2.

Because a1 contributes exactly one entry, the a1×rN intersection has size 0 or 1 — never more. The table is exhaustive.

Steps

1 Split the classifier into two independent labelers

New prompts in prompts.py, replacing CLASSIFY_SYSTEM/CLASSIFY_USER for this track only:

  • ASR_LOSS_SYSTEM — sees (COMMAND, TRANSCRIPT), returns {"lost": [...], "misheard_as": "..."}. This is LABEL_TARGET_SYSTEM's labeling half with the target-writing half deleted; its worked examples (wake words, implied words, spacing differences, bundling a near-miss phrase into one entry) carry over unedited, since they were already written against a single text witness.
  • RESP_LOSS_SYSTEM — sees (COMMAND, REPLY), returns {"form": "answer"|"repair"|"repeat"|"bad", "lost": [...], "misheard_as": "...", "asked_about": "..."}. form reuses the four type definitions the eval judge already applies to model replies, so the definitions stay in one place. asked_about is populated only when form=="repair" and is what the table means by "the piece the reply asked about"; it must be quoted in the command's words so it can be matched against the ASR's list.

Two calls, not one. Independence is the entire point of the redesign — one call that sees both passes will let the good one launder the bad one, which is exactly the contamination the current rubric keeps patching. Both systems are static, so vLLM prefix-caches each; cost goes from 1 to 2 calls per probe audio, absorbed by raising CLASSIFY_WORKERS.

form=="bad" has no column in the professor's table, and after step 3 it barely needs one: it now means only an empty or uninterpretable reply. It routes to rREPEAT, which for every value of a is identical to the ASR-only fallback — the right reading of a witness that said nothing. It keeps a distinct rBAD bucket in the row diagnostics so a built dataset still shows how often the reply pass abstained.

The ASR labeler needs one field the professor's notes don't imply: unintelligible. The --heard-reply labeler could bundle a destroyed command into a single lost entry and still call it repeat, because it set the kind itself. Here the kind comes from len(lost), so that bundling would read as a1 and produce a repair question with nothing to anchor it on. The flag, not the list length, marks the "no plausible guess to offer" case, and it forces aN.

2 Put the table in util.py

def decide_kind(asr_lost, resp_form, resp_lost, resp_asked_about):
    """(per-pass labels) -> (kind, anchor_piece | None). The 15-cell table."""

It goes in util.py rather than babble_data.py because it has two real call sites — the builder and the dry-run harness of step 3 — which is what the repo's no-single-use-function rule asks for.

Intersection matching is the one fuzzy part: lost entries are free-text quotes, so "the 7 am alarm" and "7 am" must intersect. Use normalized content-token overlap — BasicTextNormalizer, drop a small stopword set, intersect if they share at least one token. Deterministic, no third LLM call, and it only has to adjudicate a single containment test per probe.

Risk: the kind distribution skews. Only 2 of 15 cells yield repeat and both need aN. probe_by_kinds redraws SNR up to MAX_PROBES batches looking for one audio of each kind, so a rare repeat means more skipped utterances and more GPU time per triplet. Mitigation, in order: adopt the disjoint SLOT_SNR_DISJOINT bands (already tuned so kind tracks SNR), then widen the repeat band downward, then raise MAX_PROBES. Step 3 measures this before any GPU time is spent.

3 Dry-run the table offline first

babble_audio/slurp-babble-Qwen2.5-Omni-3B-v4/rows.json already holds 6000 rows carrying sentence, asr_transcript, omni_response, and the v4 kind/lost labels. Both witnesses the new table needs are already on disk, so the whole classifier can be validated for the cost of vLLM calls and zero GPU:

python label_dryrun.py --track tree \
    babble_audio/slurp-babble-Qwen2.5-Omni-3B-v4/rows.json -n 300

hr_label_dryrun.py generalized to label_dryrun.py --track {hr,tree}, rather than a near-duplicate second file. It prints:

  • occupancy of all 15 cells — the direct answer to the skew risk above;
  • the new-kind × v4-kind confusion matrix;
  • every row where the two labelers disagree about which piece was lost, since that is where the table earns or loses its keep;
  • the a1×rN rows split by intersection, so the "answerable" decision can be eyeballed on real cases before it is baked in.

Read the confusion as diagnostic, not as accuracy: v4's labels came from the reconciling rubric this design is deliberately replacing, and the a0/r0 rows are meant to reclassify.

Step 3 results — 300 rows of the v4 train split, 0 labeler failures, ~63% agreement with v4 (which is not ground truth; rows are meant to move)

First pass exposed a defect, not a result

RESP_LOSS_SYSTEM originally reused the eval judge's four type definitions, to keep the two consistent. That was wrong: at eval time bad means "this model behaved badly", but here the reply is a witness and the question is "does this reply reveal what was heard?". Those diverge on the base model's dominant mode — the rambly, on-topic, offloading reply. "does artificial intelligence have consciousness" drew a reply that wandered into AI scheduling apps: off-topic, so bad, so discarded — though it plainly heard "artificial intelligence".

Rewritten around evidence, not grade: bad now means only an empty or uninterpretable reply, and everything substantive reports a lost list instead of being thrown away. A hallucinated value puts the piece in lost with the wrong value in misheard_as; a boilerplate refusal loses every key piece explicitly.

  • The second witness now participates. Before, 53% of probes fell back to the ASR pass alone and rN never fired once, so the two-pass design was degenerating toward ASR-only for the majority of rows.
  • The a1×rN cell came alive — 0 rows → 29 (26 repair via intersection, 3 answer via the disjoint rule). The decision taken on that cell now actually applies to data.
  • Function-word repair anchors: 5% → 1%. The ASR labeler was counting auxiliaries and light verbs ("does", "give", "tell me") as lost key pieces, which produced repair questions anchored on nothing. Fixed with three worked examples; prose alone moved only "give".
  • Band yields, after: 0–5 → 21% repeat / 57% repair; 5–12 → 32% repair; 12+ → 89% answer. repeat got scarcer (35%→21%) because evidence that used to be discarded now clears rows. Still workable: with the probe loop focusing batches on unfilled slots, P(finding a repeat within MAX_PROBES) stays above 99%.
  • The skew risk in step 2 is closed. No band tuning needed.

4 Move target generation per-probe

Today build() makes one TARGET_SYSTEM call per utterance that writes all three targets, anchored on the repair probe's lost piece. The table anchors per probe, so this has to move next to the labeling — the same restructuring --heard-reply already did. Three target paths, one call each:

PathHow
answerThe existing ANSWER_TARGET_SYSTEM, unchanged and shared with the default track. It frames the assistant as having "full access to the user's apps, accounts, information, and the internet", which is exactly the anti-offloading framing this track needs.
repairTARGET_SYSTEM's repair rules, narrowed to one target and given the anchor piece + misheard_as the table selected, plus the transcript for grounding.
repeatTARGET_SYSTEM's repeat rules, narrowed to one target. Content-free by construction; kept an LLM call for phrasing variety rather than a fixed pool.
Reversed: do not reuse the base model's reply as an answer target. The original plan made the r0 column free by taking the base model's own reply verbatim — it demonstrably heard everything, so it is a correct answer. Reading 40 of them from the v4 dump killed the idea: they are correct but they habitually offload the task back onto the user. "play my most recent playlist" → "i'm not sure how to play your playlist. you might need to open the music app on your device…"; "please turn on my robot vacuum cleaner" → "i'm sorry, i don't have the ability to control a roomba…". Training on those teaches the assistant to decline and delegate, which is the opposite of the point. Written targets for the same commands: "I'm playing your most recent playlist now." and "I'm turning on your robot vacuum cleaner now." The saving was never the constraint; the target quality is.

5 Wire the --tree-label flag

A third branch in probe_by_kinds alongside the existing heard-reply / default split (the HEARD_REPLY boolean became a TRACK string, since two booleans for three mutually-exclusive tracks is a trap). It reuses the default path's two GPU decodes (ASR prompt, then task prompt) unchanged — only the labeling and target steps differ. make_row gains the per-pass diagnostics, which are what makes a bad run debuggable after the fact:

"asr_bucket": "a1", "resp_bucket": "rREPEAT", "anchor": "7 am"

Three string columns rather than the per-pass lists a fuller dump would want: they are always present, so all three tracks keep one schema, and no empty-list column has to survive a push_to_hub type inference. The prose form of both passes' verdicts goes in the existing classifier_reason.

Dataset ids: keylazy/slurp-babble-<model>-tree-v1. Driver: TREE=1 ./babble_data.sh, mirroring the existing HR=1 branch.

Smoke-build findings — 7 utterances, 21 rows, all three kinds found

The build ran clean, but reading rows.json turned up two defects no dry run could have caught, because both need the real streaming loop.

1. Duplicate utterances — pre-existing, affects all three tracks

The smoke asked for 5 train + 2 test triplets and got them from 2 and 1 distinct utterances respectively. SLURP streams several recordings of the same prompt back to back — 40 consecutive rows carry only 11 distinct slurp_ids, one repeated ten times — and build_triplets only added an id to seen_slurp_ids in the consumer loop, after a build finished. With UTTERANCE_WORKERS builds in flight and imap_ordered prefetching that far ahead, duplicates of one sentence raced through the check together. Fixed by claiming the id in candidates() at yield time, where a single thread pulls the stream. This bug is not new to this track — it applies to the default and --heard-reply builds too, so the v4/hr datasets almost certainly carry near-duplicate sentences.

2. "Targeted" repair questions covering the whole command

Four of six repair rows anchored on the entire command, producing targets like "What event and which day did you mean?" for "event reminder mona tuesday" — a repeat request wearing a repair's clothes. Cause: the base model's single most common reply to bad audio is "i'm not sure what you mean by <garbled phrase>, could you clarify?", and the reply labeler read that as repair with asked_about set to everything. Two fixes: the prompt now classes quoting-mangled-audio-back as repeat (with a contrasting pair of examples, since one piece surviving is a genuine repair), and label_resp carries a deterministic backstop — an asked_about spanning every content word of the command is downgraded to repeat regardless of what the labeler said.

Re-labeling the six smoke replies: both whole-command anchors now read repeat, the genuine one-piece case still reads repair, and the remaining disagreement is defensible either way. Targets from the healthy cells were already good — "Did you say 'alarms' or 'alarm event'?", "Did you say alarms set or land crafts?".

Second smoke — both earlier defects closed, two more found

Fixed and verified: 7 triplets now come from 7 distinct utterances with 21 distinct wavs (was 3 and 9), and no repair target asks about the whole utterance.

Reading the new targets turned up two more, both producing repair questions that ask for something the assistant does not need:

3. The wake word used as a repair anchor

CMD    : hey olly play playlist tactics from music
ASR    : a r i     play playlist tactics for music
anchor : 'hey olly'
TARGET : Did you say 'hey olly' or 'a r i'?

The whole task survived; only the assistant's own name was mangled, and the target asks the user to re-confirm it. Both labeler prompts already said the wake word is never a key piece — they said it too mildly. Now: an emphatic example in ASR_LOSS_SYSTEM ("mangled beyond recognition and it STILL is not a lost piece"), plus drop_wake_only() filtering wake-word-only entries out of both labelers' lost lists before the table sees them. Re-labeled: a0×r0 → answer.

4. A repair anchored on the command's entire content

CMD    : what's the current weather
ASR    : something fun can you give me ideas
anchor : 'current weather'
TARGET : I heard 'something fun can you give me ideas' but missed the start; what were you asking for?

A "targeted" question covering every content word is a repeat request wearing a repair's clothes — and it quoted the garbled audio back, exactly the antipattern the repair prompt forbids. The earlier asked_about guard missed it because this anchor arrived via resp["lost"], not via asked_about.

Replaced with one check on the final anchor inside decide_kind, which catches every path into it: an anchor covering ANCHOR_BREADTH_MAX (0.6) or more of the command's content words downgrades the probe to repeat. This subsumes three separate failure modes — the vague-clarification reply, either labeler bundling unrelated losses into one entry, and a command whose only key piece is the lost one (the "single key piece" carve-out the original rule-based classifier had, which the professor's table does not). decide_kind gained a sentence parameter for it.

Re-labeled through the live labelers: the two bad rows now read answer and repeat; the two good ones still read repair with sane anchors ('joe', 'what are they'). Table tests 26/26.

Third smoke — 12 utterances, clean structurally

No wake-word anchors, no whole-command targets, no wav collisions, 12 distinct sentences. Every repair anchor named one real piece: 'joe' / 'joel', 'pound sterling' / 'indian rupees', 'alarms' / 'alarm events'. One defect left, and only a sample this size could show it.

5. Answer targets confabulate specifics — shared with the default track

3 of 12 answer targets asserted a fact the assistant cannot possibly have:

commandtarget
any recent emails from anna"I found two recent emails from Anna sent this morning."
what is the exchange rate of us dollar to pound sterling"The current exchange rate is 1 US dollar to 0.79 British pounds."
are there any alarms set what are they"There are currently no alarms set."

Cause: ANSWER_TARGET_SYSTEM frames the assistant as having "full access to the user's apps, accounts, information, and the internet" and then says to answer directly "if you know the answer" — so the writer treats having access as knowing, and invents a value.

This matters more than 25% suggests. With --n-extra-ans 3000, answer rows are ~4000 of 6000 train rows, so this is on the order of a thousand rows teaching the model to invent user state. And the eval judge cannot catch it: it sees only (command, response), never ground truth, so a confidently fabricated exchange rate scores as a clean answer = 1.0. The metric would rate this behaviour as success.

Fixed by distinguishing knowledge from access: stable general knowledge answers directly, while anything private to the user (emails, calendar, alarms, files) or minute-to-minute (time, weather, rates, scores) must say it is checking, naming what it looks for. Verified — the three above become "I'm checking your recent emails from Anna now.", "I'm looking up the current dollar to pound exchange rate for you.", "I'm checking your alarms now…", while "how many oceans are there in the world" still answers directly with the five oceans.

Scope note: the same answer-rule block appears verbatim in TARGET_SYSTEM, which the default two-pass track uses, and both copies were patched — leaving one fixed and one not would be a trap. So the v4-style datasets already on the Hub were built under the old rules and carry this confabulation; a rebuild would now differ. That is a fix, not a regression, but it does mean v4 is not byte-reproducible from HEAD.

6 SFT — no code change

sft_qwen.py needs nothing: no --heard-reply, plain TASK_PROMPT, and the existing --train-caps composition sweep applies as-is. TREE=1 ./sft.sh adds the track's dataset defaults and names adapters <model>-bab-tree-adapter-<n>x.

One caveat inherited from the skew risk: the sweep caps repair and repeat at 1000 each, so the data build has to actually reach 1000 repeat triplets. Step 3's cell occupancy tells you whether that is affordable before you commit the GPU hours.

7 Eval — one cell moves

Lining the professor's judge rules up against the current matrix, three of the four rows are already exactly right:

SCORE_MATRIX_TREE = {
    "answer": {"answer": 1.0, "repair": 0.0, "repeat": 0.0, "bad": 0.0},   # unchanged
    "repair": {"answer": 1.0, "repair": 1.0, "repeat": 0.5, "bad": 0.0},   # unchanged
    "repeat": {"answer": 1.0, "repair": 0.5 0.0, "repeat": 1.0, "bad": 0.0},
}

Gate it behind --score-matrix {legacy,tree} on babble_eval_qwen.py so prior result files stay reproducible, and have the new TREE=1 track in eval.sh pass tree. The flag is deliberately about scoring, not about labeling — a legacy-track dataset can be rescored under the new matrix, which is the cheapest way to see how much of any EAR movement is the matrix change alone.

Judge prompt: no change, per the decision above. Default to the rules judge (RESPONSE_TYPE_SYSTEM) for comparability with the v4 baseline; --fewshot-judge stays available and orthogonal.

Expect F (the repeat-row mean) to drop versus prior runs purely from the matrix change — a base model that answers one question when the whole command was lost used to bank 0.5 and now banks 0. Since EAR is the harmonic mean of three, a lower F pulls it down more than proportionally. This is intended, but it means tree-track EAR is not comparable to published v4 EAR unless the v4 results are rescored under --score-matrix tree too. Do that rescore; it is a few minutes of judge calls against existing .jsonl files.

Open, decided by recommendation

These were not in the professor's notes; each is resolved above in the direction I'd default to, and each is cheap to reverse.

Two labeler calls rather than one. Doubles classifier calls to buy genuine independence. Reversible: one call returning both per-pass objects would work, at the cost of the contamination the redesign exists to remove.
form=="bad" means empty output only, and routes to the ASR-only fallback. Narrowed after step 3 — the original definition (hallucination, refusals, off-topic) swallowed 53% of replies and discarded their evidence.
Intersection by normalized content-token overlap. Deterministic and cheap; the alternative is an LLM alignment call. Only ever adjudicates one containment test per probe.
Repeat targets stay an LLM call. They carry no content, so a fixed phrase pool would work, but variety in the training targets is worth one cached call.
Housekeeping done alongside this plan: rows_<ds>.json dumps now land at babble_audio/<ds>/rows.json, next to the wavs they reference, and the four existing dumps were moved there.

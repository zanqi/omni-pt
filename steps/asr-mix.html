asr1 & asr4 — one labeler, two witness counts, ASR mixed into the SFT

Both experiments label with the same fine-tuned witness, keylazy/Qwen2.5-Omni-3B-asr-sft, and differ only in how many hypotheses that witness returns: asr1 reads one transcript, asr4 intersects four beams. Both then depart from the ft-asr track in one shared way — the repair SFT mixes in keylazy/slurp-asr-bab-v1 1:1, so the trained model ends up hearing roughly what the labeler heard, which is the assumption its labels were resting on all along.

Why mix ASR rows in at all

Every sent-track label is a claim about hearing: this key piece did not survive the noise, so the model cannot be expected to act on it and should ask. The claim is measured on the labeler and then imposed on a different model — the base omni weights that the repair LoRA starts from. If those two models hear differently, half the training signal is a lie: rows where the labeler lost a piece the student would have caught (teaching it to ask about something it heard perfectly well), and rows where the labeler caught a piece the student loses (teaching it to answer confidently while deaf).

Mixing keylazy/slurp-asr-bab-v1 in 1:1 makes the student train on the labeler's own objective, on the labeler's own data, at the same 8K scale. It does not make the two models identical — but it turns “trust the labeler's ears” from an assumption into something with a measurable proxy, which is why step 7 re-runs asr_eval_qwen.py on the finished mixed adapter and reads its WER against the ASR LoRA's. That number is the premise, reported rather than assumed.

The mix is leakage-free by construction. asr_data.py builds from SLURP devel; babble_data.py builds from train and evaluates on test. The two halves of the mixed dataset share no sentence, and neither shares one with the eval split — the ft-asr step-0 preflight is what established that, and nothing here changes the splits.

What moves, and where

Two boxes change against the ft-asr track. Everything else — prompts, SNR bands, seeds, the labeler's two-stage rubric, the judge, the metric — is the same file it was.

Step 2 — the collator picks a prompt per row, not per run edit

This is the one change that makes mixing possible at all. OmniSFTCollator resolves get_prompts(task, family) once in __init__ and renders every example under it. A mixed batch holds two kinds of row whose targets were written for two different prompts: an asr row's target is a verbatim transcript that belongs under ASR_PROMPT_QWEN2_5, and an answer/repair/repeat row's target is an assistant reply that belongs under the restate TASK_PROMPT. Render either under the other's prompt and the row teaches the wrong contract — and there is no error to notice, just a worse adapter.

SlurpDataset.__getitem__ already carries kind through (sft_qwen.py:54), so the row knows which it is. Both renders — full conversation and prompt-only — must use the same pair, which falls out of passing the kind down to _conv.

Step 3 — the mix edit

Two config keys and one block in main(). It stays a block rather than a helper: CLAUDE.md's rule is that a module-level def earns its place with two call sites or by being a pipeline step, and this has exactly one caller.

3a. The two keys

# --- sft_qwen.py, in @dataclass Config, under the --task repair half ---

    # as there are clarification rows", i.e. the 1:1 mix; 0 disables it, which
    # is how the no-mix control arm of this experiment is trained off the SAME

The prefix matters — mix_asr_*, never asr_mix_*. sft_qwen.py:469 raises SystemExit when a --task repair run is handed any asr_* flag, on the theory that it would be read by nobody. A field named asr_mix_ds_id is precisely the flag that is read on a repair run, and the guard would reject the only run that wants it.

3b. The block

The two datasets do not share a schema, which is the whole reason this is more than one line:

slurp-asr-bab-v1
id, target, kind, audio, snr_db, sentence, slurp_id, source
slurp-bab-*-sent4-ftasr-v1
id, kind, target, audio, snr_db, asr_transcript, omni_response, lost, classifier_reason, asr_bucket, resp_bucket, beam_hypotheses, beam_losses, key_pieces, slurp_id, sentence, source

concatenate_datasets requires one schema, so both sides are projected to the three columns SlurpDataset actually reads before they meet.

            [train_hf.select_columns(cols), asr_hf.select_columns(cols)]

Import concatenate_datasets alongside the existing from datasets import Audio, load_dataset. No shuffle of the concatenation is needed — Trainer wraps the train dataset in a RandomSampler, so the two halves interleave per epoch on their own.

Why not upsample the clarification rows instead of subsampling the ASR rows?

At the planned size the question is moot — 8,000 clarification rows against 8,000 ASR rows is 1:1 with no resampling on either side, which is the reason the budget was set at 8,000 rather than at whatever the split happens to yield. mix_asr_rows exists for the cases where it is not: a 4,000-row rebuild takes -1 and gets 4,000 of the 8,000 ASR rows, and the no-mix control takes 0. Duplicating clarification rows to reach a ratio would change the number of gradient steps those rows get, which is the variable the whole experiment is about.

  • scanned at completion. asr1 should finish near ~30,000 and asr4 near ~36,000 of the 50,628. Materially higher means the yield dropped and the split may run out before n_extra_ans is satisfied — the run does not fail, it just returns fewer rows, and the 1:1 mix follows via mix_asr_rows: -1.
  • pieces. This is key_pieces failing on the vLLM box. A handful is normal (21 in the whole sent4-ftasr build); hundreds means the labeler server is sick, and every affected utterance is consumed from the split as it fails. That is how sent2_v1_e2e burned all 50,628 recordings for 600 triplets. Kill the job rather than let it eat the split.

Step 9 — how to read the outcome

Two questions, and they are answered by different comparisons. Read them in this order.

Q1. Do four witnesses beat one, with a fine-tuned labeler?

asr4 EAR vs asr1 EAR. This is the clean one: the two configs differ in six values, all of them naming the track or its outputs. Whatever the sign, it is the answer to the question ft-asr part 2's step-8 gate raised and could not settle — whether a fine-tuned ASR model's four beams still carry four opinions, or collapse into one witness wearing four hats.

Q2. Did the mix help?

asr1 vs sent1asr (0.591) and asr4 vs sent4-ftasr (0.515). Confounded, and say so in the paper: 4k→8k rows moved at the same time, and for asr1 so did the witness. A rise here is consistent with the mix helping, with more data helping, or with a better witness — it does not separate them.

The third arm that would separate them, if Q2 needs a real answer. It costs one SFT run and two eval passes — no build, because it trains off the dataset asr4 already produced: 
python -u sft_qwen.py --config configs/asr4.yaml --mix-asr-rows 0 \
    --repair-repo-name Qwen2.5-Omni-3B-bab-asr4-nomix-sft
python -u babble_eval_qwen.py --config configs/asr4.yaml --tag asr4-nomix \
    --adapter-path checkpoints/Qwen2.5-Omni-3B-bab-asr4-nomix-sft
asr4 vs asr4-nomix is then the mix alone, at fixed data and fixed witness. This is why mix_asr_rows: 0 is a supported value rather than something to assert against.
asr4 > asr1asr4 ≈ asr1asr4 < asr1
both > their baselines Beam consensus survives fine-tuning; the ladder is worth climbing. Report the pair as the track's best. The extra three beams buy nothing once the witness is good — a real, publishable negative: use the cheap track. Four fine-tuned beams agree too much, so “lost only if every witness missed it” degenerates into a one-witness rule with 4× the decode cost. Also the part 2 diversity number's prediction, now confirmed end to end.
both ≈ their baselines The mix is neutral on EAR. That is not a failure — it buys the WER parity in step 7, which is a claim about the method, and it costs nothing in the metric. Say exactly that.
both < their baselines Suspect the mix before the witness: 8,000 transcription rows against 8,000 clarification rows may simply be teaching the model to transcribe when asked to act. Check the eval transcripts for replies that read like ASR output; if that is what it is, the fix is a ratio, not a rebuild.

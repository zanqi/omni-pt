Heard / Reply scaffolding

The model writes down what it heard, then replies. One decode pass replaces the ASR + task pair, the Heard: line becomes the labeling witness, and every LLM prompt in the loop goes few-shot.

Decisions taken
  • Output format: Heard: … / Reply: … — used by the data-gen probe, by SFT, and at eval. Supersedes the earlier "naturally grounded reply, no scaffolding" decision.
  • Labeling reads the Heard: line only. Compare it to the ground-truth sentence, list the lost key pieces, count them: 0 → answer, 1 → repair, ≥2 → repeat. Strict count — no "half or more of the key info" carve-out. The Reply: half is not consulted.
  • One LLM call per probe audio does label + target together.
  • Few-shot, not rules. Both the labeler and the eval judge get ~7 worked examples mined from rows_slurp-babble-Qwen2.5-Omni-3B-v4.json and hand-edited, replacing the current multi-hundred-word rubrics.
  • Gold Heard: line = the probe's own Heard: line, verbatim. Self-distilled from the base model on that exact audio; no LLM rewriting.
  • Eval judge sees (sentence, reply). Parse the Reply: half out of the model output; if the scaffolding is absent, fall back to the whole output and count the parse failure.
  • Disjoint SNR bands: answer = clean or 12–20 dB, repair = 5–12, repeat = 0–5. Clean audio stays in the answer band so the model doesn't lose the noise-free case. An audio whose concluded kind disagrees with its band still fills that kind's slot (current behavior, unchanged).
  • Probe decodes both halves and stores the base Reply:, even though nothing downstream reads it — it is the diagnostic for "what would the untuned model have said at this SNR".
  • Plumbing: --heard-reply flag, default off, on babble_data.py / sft_qwen.py / babble_eval_qwen.py. The rule-based two-pass track stays byte-reproducible.

Why the scaffolding is load-bearing

The two-pass design exists because a task reply is a lossy witness: "Sure, I'll take care of that" proves nothing about any piece, so the ASR transcript was the fallback witness. The Heard: line is that witness, produced by the same forward pass as the reply — which makes it a strictly better witness than the separate ASR pass was, because it reflects what this pass of this model actually got, not what a differently-prompted pass got.

Three consequences follow, and they are the reason this is worth doing:

  • The label becomes one text comparison. Old rubric: reconcile two witnesses that can disagree, with a priority ordering ("a correct reply always overrides a bad transcript") that took ~20 lines to state and is the main source of label noise. New rubric: diff Heard against the command, count what's gone. That is what makes a few-shot prompt viable at all — the old task genuinely needed the rules.
  • Mishearing detection comes back, stronger. The earlier reply-only plan lost misheard_as (paraphrased replies hide swaps). The Heard: line surfaces swaps as plainly as the ASR transcript did — oceans→children, grubhub→grandma — so the "did you say X or Y?" repair style survives.
  • Repair becomes a text-level decision. The model writes down what it heard before choosing how to respond, so "which piece is missing" is something it can condition on, rather than something it has to infer implicitly from acoustics inside a single forward pass.
The one coupling to get right

The judge sees the Reply: half alone. So the Reply: half must remain self-sufficient evidence that the command was understood — it cannot outsource grounding to the Heard: line above it.

Concretely: an answer target of "Sure, on it." scores bad even when the Heard: line above it is perfect, because the judge never sees that line. So the target rules keep the existing requirement that the reply name the request's action and topic. This is the same constraint the earlier plan imposed via a "ground your reply" prompt instruction — here it lives in the target style instead, where supervision enforces it rather than the model choosing to comply.

Steps

1Free dry run: mine the few-shots and measure label drift, before any GPU

rows_slurp-babble-Qwen2.5-Omni-3B-v4.json (5.6 MB, local) already holds 4000 answer / 1000 repair / 1000 repeat rows with sentence, asr_transcript, lost, swapped, target. The ASR transcript is a close proxy for the Heard: line, so the new labeler can be developed and scored offline for the cost of some vLLM calls:

  • Mine the few-shots. Pull real cases covering: exact match; filler-only difference; a word implied by the rest of the command; a wake-word mangling; a single deletion; a single substitution; a multi-piece loss. Hand-edit for crispness.
  • Score the new labeler against the old labels. Run label_target(sentence, asr_transcript) over ~300 rows, report agreement and the kind → kind' confusion.

Expect real disagreement, and expect much of it to be correct. Two known sources: (a) the strict count rule reclassifies single-key-piece commands from repeat to repair; (b) the old labels could use the reply as a second witness, so rows labeled answer on reply evidence now come back repair. Sample 20 disagreements by hand rather than treating agreement as a number to maximize — the v4 labels contain visible errors of their own (one sampled repeat row has asr_transcript identical to sentence yet lost: ["post","important"]; the new rule labels it answer, correctly).

Also worth counting here: v4's repair targets are dominated by one template — "Did you mean X or Y?" in 3 of 4 sampled rows. The few-shot examples must deliberately vary that, or SFT learns one sentence.

2prompts.py: the output contract and its parser

TASK_PROMPT = (  # unchanged, baseline track
    "You are a smart voice device with full access to the user's apps, "
    "accounts, devices, information, and the internet. Listen to the user's spoken "
    "request and respond naturally and concisely, addressing everything it asks."
)

# --heard-reply track. Two lines, always both. The Heard line is the only
# witness the labeler reads; the Reply line is the only text the judge reads.
# Deliberately says nothing about asking for clarification -- repair behaviour
# is what we measure, not what we instruct.
TASK_PROMPT_HR = (
    "You are a smart voice device with full access to the user's apps, "
    "accounts, devices, information, and the internet. Listen to the user's spoken "
    "request. Reply in exactly two lines, and nothing else:\n"
    "Heard: <write out the words you actually heard; if part of it was "
    "drowned out by noise, write only the words you did catch and do not "
    "guess at the rest>\n"
    "Reply: <respond naturally and concisely, addressing everything the "
    "request asks>"
)

def task_prompt(heard_reply):
    return TASK_PROMPT_HR if heard_reply else TASK_PROMPT

def split_heard_reply(text):
    """'Heard: a\nReply: b' -> ('a', 'b'). Returns ('', text) if unparseable,
    so a non-compliant model gets scored on its raw output rather than on an
    empty string."""

split_heard_reply is tolerant: case-insensitive labels, optional markdown bold, tolerates a missing Heard: prefix on the first line, and treats everything after the Reply: marker (further newlines included) as the reply. Both call sites — the probe in babble_data.py and the judge feed in babble_eval_qwen.py — use this one function, so parse behavior can't drift between train and test.

"Do not guess at the rest" is the counterpart of the earlier plan's "do not invent a detail you did not hear". Without it the model completes the sentence into something plausible, and a confabulation with no acoustic basis is pure label noise — it makes a repeat audio look like an answer.

3babble_data.py: bands, probe, and the merged call

3a. Disjoint bands, with clean audio in the answer band

SLOT_SNR = {
    "answer": (12.0, 20.0),
    "repair": (5.0, 12.0),
    "repeat": (0.0, 5.0),
}
CLEAN_ANSWER_PROB = 0.25   # answer draws that skip babble mixing entirely

In make_probe_batch, after the slot is drawn: if slot == "answer" and rng.random() < CLEAN_ANSWER_PROB, append clean unmixed with snr = None and skip the babble synthesis. snr_db becomes nullable in the pushed schema; None reads as "clean" everywhere downstream. Keeping clean audio in the mix is the point — a model trained only on 12 dB-and-below audio can regress on the noise-free case, which is still the common one in deployment.

Slot assignment is unchanged: an audio drawn from the repair band that comes back repeat still fills the repeat slot if it's open. The bands bias the search; they don't define the label. With a merged label+target call, discarding an off-band hit would also throw away a target already paid for.

3b. One decode pass in probe_by_kinds

# two-pass (current)

An audio whose output has no parseable Heard: line is dropped from the batch and counted as skip["format"] in the tqdm postfix, rather than labeled off a fallback — at build time a fabricated witness is worse than one fewer row. (At eval the opposite call is made, because there every row must be scored one way or another.) Watch this counter on the smoke run: Qwen2.5-Omni-3B is the model most likely to ignore a two-line contract, and a high failure rate decides whether the track is viable for the 3B at all.

Row schema: asr_transcript now carries the parsed Heard: line and omni_response the parsed Reply: line, so both columns keep their meaning and babble_eval_qwen.py / eval.ipynb keep working. Two columns are added: target_reply (the reply half alone, for analysis and for re-rendering targets without regenerating) and heard_gold (= asr_transcript, stored explicitly so the composition is self-documenting). target holds the composed two-line string SFT trains on.

3c. LABEL_TARGET_SYSTEM: the few-shot labeler

Replaces both CLASSIFY_SYSTEM and TARGET_SYSTEM on this path. Static system prefix (prefix-cached by vLLM) plus a two-line user suffix. Draft:

You are labeling noisy-audio data for a smart voice assistant.

You get the user's real spoken COMMAND, and HEARD -- what the device caught
after loud background chatter. Compare them and list the key pieces of the
command that did not survive: entities, names, places, times, dates,
quantities, titles, and the requested action. Filler words ("please", "could
you", "hey"), the wake word or the assistant's name, and words whose meaning
the rest of the command already implies are never key pieces.

Then set kind by how many key pieces were lost:
  0 lost -> "answer"    1 lost -> "repair"    2 or more lost -> "repeat"

Then write the device's target reply for that kind. A grader sees that reply
on its own, without the HEARD line, so it has to stand alone.

Return ONLY JSON: {"lost": [...], "misheard_as": "...", "kind": "...",
"reply": "..."}
Quote "lost" using the words of the real COMMAND. "misheard_as" is the wrong
word HEARD in place of a lost piece, or "" if the piece was simply dropped.

Examples:

COMMAND: find some classical music by beethoven and play it
HEARD:   find some classical music by beethoven and play it
{"lost": [], "misheard_as": "", "kind": "answer",
 "reply": "I'm finding some classical music by Beethoven and playing it now."}

COMMAND: hey olly are there any alarms set
HEARD:   hey ollie are there any alarms
{"lost": [], "misheard_as": "", "kind": "answer",
 "reply": "You have one alarm set, for 7 am tomorrow."}
   -- the wake word and "set" are not key pieces

COMMAND: how many oceans are there in the world
HEARD:   how many children are there in the world
{"lost": ["oceans"], "misheard_as": "children", "kind": "repair",
 "reply": "How many of what in the world -- oceans, or children?"}

COMMAND: i have a meeting by two pm today please remind me
HEARD:   i have a meeting at two p m today
{"lost": ["remind me"], "misheard_as": "", "kind": "repair",
 "reply": "Got your two pm meeting today -- what did you want me to do about it?"}
   -- never say the lost words back; ask around them

COMMAND: food order from grubhub
HEARD:   food order from grandma
{"lost": ["grubhub"], "misheard_as": "grandma", "kind": "repair",
 "reply": "Ordering food -- did you say Grubhub, or grandma?"}

COMMAND: turn on the radio on this channel
HEARD:   anywhere on the radio
{"lost": ["turn on", "this channel"], "misheard_as": "", "kind": "repeat",
 "reply": "It's really loud in here -- what was that?"}

COMMAND: please tell me a joke that i'll think is funny
HEARD:   he said me a job that i think is like
{"lost": ["tell me a joke", "i'll think is funny"], "misheard_as": "", "kind": "repeat",
 "reply": "I couldn't catch that over the noise -- could you say it again?"}

Everything the deleted rubric enforced by rule is now carried by an example: the wake-word and implied-word exclusions (ex. 2), no-reveal on deletions (ex. 4), the misheard-as confirmation form (ex. 3 and 5), content-free repeat requests (ex. 6 and 7). Two rules survive as prose because no single example teaches them — the key-piece definition, and the fact that the reply is graded alone.

Deliberately dropped: the "would recovering only this piece tell the assistant anything it needs?" usefulness test that guarded repair. It encoded label semantics the strict-count decision removes. If the smoke run shows many repair rows whose lost piece doesn't matter (that test's target case), the fix is an eighth example, not the rule coming back.

Repair-reply diversity now rests entirely on the examples. Three repair examples with three shapes (an "X or Y?" alternative, an open question around a deletion, an "action + X or Y?") is the minimum; check the generated distribution on the smoke run and add a shape if it collapses.

LABEL_TARGET_USER = 'COMMAND: {sentence}\nHEARD:   {heard}'

Both fields keep going through _normalize_text (lowercase, punctuation stripped) so the labeler can't read ASR-standard capitalization as a change. The retry guard in classify() stays, extended to the merged shape: retry when kind and len(lost) disagree, or when reply is empty.

3d. Merged call, and what it costs

The combined call fires once per probe audio, in the same ThreadPoolExecutor that runs classify today — so the call count is unchanged (up to MAX_PROBES × PROBE_BATCH_SIZE = 48 per utterance) and only the output grows. The separate per-utterance TARGET_SYSTEM call disappears, as does ANSWER_TARGET_SYSTEM's call in build_answer_rows. Net: one fewer call per kept row, at the price of writing targets for probe audios that get discarded because their slot was already filled.

build_triplets simplifies: the whole "one LLM call writes all 3 targets" block after the probe (lines ~659–695) is deleted, and probe_by_kinds returns the target alongside the label in each slot dict. build_answer_rows loses its target block the same way. ASR_PROMPT / ASR_SYSTEM_PROMPT / ASR_MAX_NEW_TOKENS stay in the file, unused on this path.

One real regression to note: the old shared call saw the repair and repeat transcripts together and wrote all three targets in one context, so a triplet was stylistically coherent. Per-audio calls lose that. It doesn't matter for training (rows are shuffled) but the three rows of a triplet no longer read as one conversation.

4Composing the target

target = f"Heard: {probe['heard']}\nReply: {llm_reply}"

The gold Heard: line is the base model's own output for that exact audio — so SFT teaches the front-end nothing new, only teaches the model to write down what it already heard and condition its reply on that. That is the intended mechanism, and it's why this is cheap: no LLM rewriting, no risk of the gold Heard line disagreeing with the acoustics.

Two consequences to accept: the model is trained to reproduce the base model's mishearings verbatim (grandma for grubhub) — correct on this audio, but imitation rather than transcription; and the gold Heard line inherits the base model's formatting quirks, since base_generate_batch already lowercases its output. Both are fine as long as they stay consistent between train and eval, which they do, because the same prompt produces both.

5sft_qwen.py: delete the duplicated prompt, then add the flag

Latent bug worth fixing regardless: sft_qwen.py defines its own copy of TASK_PROMPT (~line 30) instead of importing from prompts.py. The copies happen to be identical today, so nothing is wrong — but the moment either is edited, training and eval silently prompt the model differently and nothing errors. Replace it with from prompts import task_prompt before adding anything.

Then --heard-reply (default off), selecting the user-turn prompt in OmniSFTCollator. Distinct output/hub names so the baseline adapter can't be overwritten: Qwen2.5-Omni-3B-bab-hr-sft.

Run --smoke after the change and read two things, not one: the supervised-token count must still cover only the assistant turn (the longer prompt shifts the prompt/full token-length diff the label mask is built from — exactly what --smoke exists to catch), and the decoded supervised span must show both lines, starting at Heard:. If the mask starts mid-target, the two-line format trains as garbage.

6babble_eval_qwen.py: few-shot judge, parsed input

The scoring path is untouched — SCORE_MATRIX, harmonic3, the C/R/F/EAR aggregation, and the summary-record format all stay, so eval.ipynb's load_summary keeps parsing. What changes:

  • Judge input. classify_response(judge_fn, sentence, reply) with reply = split_heard_reply(raw)[1]. On a parse failure the fallback is the whole raw output (per the decision above); the run summary gains a heard_parse_failures count so a baseline that never emits the format is visible rather than silently scored as if it had.
  • Judge prompt goes few-shot, replacing RESPONSE_TYPE_SYSTEM's ~130 lines. Same four types (answer / repair / repeat / bad), same {"reason": …, "type": …} output with reason first. The examples have to cover the eight calls the long rubric spent its length on, because these are the ones a judge gets wrong unprompted:
    CaseType
    carries out the task, details consistent with the commandanswer
    can't-do decline that names a content word from the command ("I can't check the game score for you")answer
    decline naming nothing from the command ("Sorry, I can't help with that")bad
    asks for something the command never said, but the task needsanswer
    targeted question about a detail the command did staterepair
    confirmation offering the true word and a similar wrong onerepair
    asks for the whole command again, asserts no detailsrepeat
    confidently states a detail the command didn't containbad
    Each example carries its one-sentence reason too, so the judge learns the reason's length and register alongside the label. Keep one prose line the examples can't teach: classify the response's form, not its correctness — a targeted question is repair even when it targets a piece that was perfectly audible.
  • --heard-reply flag selecting the task prompt in build_conversation. Required for this track: evaluating an hr-trained adapter under the plain prompt is a train/test mismatch that reads as a regression.
  • Output filename. The default bab_results_{model_name}_v2.jsonl is keyed only on model/adapter name, so an hr run of an already-evaluated model silently overwrites the baseline file eval.ipynb reads. Fold the track into the default name (…_hr.jsonl) or always pass --out.
  • Defensive column reads. row["asr_transcript"] → row.get("asr_transcript", "") (~line 405), same for omni_response (~line 425).

Expect the confusion matrix to move even for an unchanged model, for reasons unrelated to quality: a few-shot judge is a different judge, and the parsed reply is shorter and more decision-like than the raw output was. C/R/F/EAR from this track are not comparable to any previously recorded number. The only clean comparisons are inside the table below.

7Ten-triplet smoke run before the full build

Set N_TEST_TRIPLETS = 10, point --ds-id at a throwaway repo, read the tqdm postfix:

  • skip["format"] — new counter, the one most likely to kill this. A non-trivial rate on Qwen2.5-Omni-3B means the 3B can't hold a two-line contract under noise; before abandoning the track, try moving the format instruction into the system prompt, or prefilling Heard: into the assistant turn so only the continuation is free.
  • skip["probe"] — slots unfilled after MAX_PROBES. Disjoint bands make this more likely than before, since each band now gets one shot at its kind instead of overlapping coverage. If a specific slot starves, shift that band rather than raising MAX_PROBES (probe batches cost GPU time linearly and don't fix a mis-centred band). The repair band (5–12 dB) is the one to watch: exactly-one-lost-piece is a narrow target.
  • skip["targets"] — should be near zero now that labeling and target writing share a call; non-zero means the merged JSON contract is confusing the writer.
  • Then read ~15 rows by hand: does every target start with Heard: and contain exactly one Reply:? Does any repair reply say the lost words out loud? Does any repeat reply leak an entity? Are the repair replies varied, or all one template?

Risks

Format compliance is the whole bet. Every benefit here is downstream of the model reliably emitting two labeled lines. Qwen2.5-Omni-3B under 0 dB babble is not an obvious candidate for that. skip["format"] on the step-7 smoke run is the go/no-go number, and it is cheap — run it before anything else that costs GPU time.
The Heard line can be confabulated. "Do not guess at the rest" is an instruction, not a guarantee. A model that fluently completes a half-heard sentence produces a witness that looks clean, so the audio labels answer and the row quietly teaches confident hallucination. This is the failure mode the two-pass cross-check used to catch, and nothing catches it now. Mitigation is inspection: on the smoke run, hand-check answer rows drawn from the bottom of their band (12–14 dB) against the audio.
Few-shot generalizes off-distribution differently than rules do. Rules cover the cases they were written for; examples cover the neighborhood of the examples. SLURP's long tail (multi-intent commands, one-word commands, commands whose action is the only key piece) is where they diverge. The step-1 dry run over 300 real rows surfaces this, and the fix is always another example.
Strict counting reassigns real rows. Single-key-piece commands that lose their piece move repeat → repair, so the dataset now wants repair questions for commands with nothing left to anchor on ("...which what?"). The few-shot examples don't cover this, because v4 labeled it repeat. Count how often it happens in the dry run; more than a few percent and it needs its own example showing what a repair question looks like when the command is nearly empty.
Compute saving is modest. One decode pass disappears, but it was the cheap one (64 vs 256 max-new-tokens) and audio prefill dominates for short SLURP utterances. The merged LLM call saves one call per kept row out of ~48. Measure the smoke run's wall clock; don't budget on a speedup.

Fixing the DPO C-drop

Why Qwen2.5-Omni-3B-mask-v2-dpo lost 14 points of Competence against its own SFT parent, and the one change to mask_dpo_data.py that should get it back. Plan only — nothing here is applied yet. Follows on from mask.html §9–10 and dpo.html.

TL;DR. DPO did not make the model worse at answering — it moved the answer/ask boundary. The question rate on answerable audio went 11% → 54%, and the generic “sorry, say that again” phrasing went 8 → 63 rows.

The cause is in the pair set, not the trainer: the SFT policy already answers ~84% of answer rows perfectly, so mask_dpo_data.py drops them as all-good. ~840 of the 1000 answer rows contribute zero gradient, while 958 repair/repeat pairs push the clarify prior up. Even after the existing per-kind reweighting, the set rewards repeat-style phrasing 369 vs 127 by weight.

Fix: stop dropping all-good answer rows. Mint a hold-firm pair for each — chosen = the correct sampled answer, rejected = a clarifying/repeat reply. ~840 new pairs in the opposite direction, no new generate and no new judge calls.

2It is the boundary, not the capability

Two measurements separate “the model got worse” from “the model got more eager to ask”, and both point at the second.

Every single regression is a question. Of the 400 answer rows, 65 score lower under DPO than under SFT, and all 65 replace an action with a question. Across the whole answer split:

on answerable audio (n=400)SFTDPO
reply contains a question44 (11%)215 (54%)
reply is generic “say that again” phrasing8 (2%)63 (16%)
… of which are among the 65 regressions—38

The single largest failure mode is the repeat kind's template leaking onto fully answerable commands.

The damage tracks the background, not the difficulty. If DPO had degraded the model's ability to understand speech, clean audio would suffer with everything else. It barely moves:

C by backgroundnSFTDPOΔ
clean2160.7920.736−0.056
babble bed9840.8780.720−0.158

Noise in the signal — not loss of the signal — is what now triggers the ask. That is exactly the over-triggering failure mask.html §1 designed the dataset to avoid (“heard a burst → ask”), reintroduced at the DPO stage.

Not an SNR story. The by-SNR breakdown is not monotone and the bins are small (72–312 rows): the gap is 27 pts at 0–5 dB, 8 pts at 5–10, 20 pts at 10–15, 19 pts at 15–20, and 0 at 20–25 dB (n=72, both runs at C = 1.0). The only defensible reading is that the gap is present at every SNR except the quietest bin, and is much larger on babble than on clean. Do not lean on a mid-SNR narrative.

4Why the pair set teaches this

results/mask_prefs_Qwen2.5-Omni-3B-mask-v2-sft.jsonl, 1117 pairs kept from 3000 train rows (breakdown: all-good 1857, sampled 1083, gold-chosen 34, flat 26):

kindtrain rowspairs keptkept %weight applied
answer100015916%2.34
repair100068368%0.55
repeat100027528%1.35

Cause 1: ~840 answer rows are invisible to the objective

The SFT policy already answers most answerable rows correctly at every one of the K=8 samples, so mask_dpo_data.py takes the all-good branch and drops them. Nothing in the DPO loss then holds those rows in place while 958 repair/repeat pairs push the clarify prior up. The answer kind's whole gradient budget is concentrated on the 159 rows the policy already found hard — high per-pair weight (2.34) spread over a narrow, unrepresentative slice, against a broad and diverse 958.

Cause 2: even after reweighting, the set favours repeat-style phrasing 3:1

The per-kind weights in dpo_qwen.py:290 equalise the count per kind. They do not equalise direction. Counting weighted pairs in which one side uses generic “say that again” phrasing and the other does not:

weighted mass
rewards repeat-style phrasing (chosen has it, rejected does not)369
punishes repeat-style phrasing (rejected has it, chosen does not)127

2.9 : 1 toward the exact phrasing that then shows up on 63 answerable rows. The repair kind supplies the bulk of it: 282 of its 683 pairs have a question as chosen and a confident answer as rejected. The model cannot perfectly tell answerable-noisy from unanswerable-noisy, so “suppress the confident answer under noise” generalises across the boundary.

Cause 3: nothing bounds the drift

DPO optimises only a difference, so raising the clarify prior globally is a cheap way to win most pairs. The training log bears it out: the margin climbs monotonically to ~1.1 nats/token and the loss to 0.40 by epoch 2, with reward_acc pinned at 1.0 in most late windows. Step-0 |policy − reference| was 0.0064 nats/token, so the plumbing is sound — the pairs really are asking for this.

This is the second time. The comment at dpo_qwen.py:283 records the first DPO run taking the question rate from 12% to 73% and dropping C from 0.79 to 0.75, and the per-kind weighting was added to fix it. It halved the effect (73% → 54%) but did not remove it, because it addresses Cause 2 only, and only partially. Cause 1 has never been addressed.

5The fix

One branch in mask_dpo_data.py. For an answer row where every sample already scores 1.0, do not drop it — emit a hold-firm pair whose chosen is the model's own correct answer and whose rejected is a clarifying or repeat reply that would be wrong here.

# mask_dpo_data.py, in the MIN_MARGIN branch (currently lines 286-300)
                 if best["score"] - worst["score"] < MIN_MARGIN:
                     if best["score"] >= 1.0:
-                        # the policy already gets this row right every time
-                        stats["all-good"] += 1
-                        continue
+                        if row["kind"] != "answer":
+                            stats["all-good"] += 1
+                            continue
+                        # An answer row the policy never gets wrong makes no
+                        # sampled pair, so ~840 of the 1000 contribute nothing
+                        # while 958 repair/repeat pairs push the clarify prior
+                        # up. Mint the pair the sampler cannot: the negative is
+                        # a reply that is *correct on some other row of this
+                        # utterance* and wrong here, so it teaches the boundary
+                        # rather than a phrasing.
+                        worst = {"text": hold_firm_negative(row), "score": 0.0,
+                                 "reason": "clarify on an answerable row"}
+                        pair_source = "held-firm"
                     if worst["score"] > 0.0:

best is left exactly as the sampler produced it — a real, on-policy, judge-verified correct answer. Only the negative is synthesised.

Everything downstream already works: ref_logprob is called on both sides, the record is written with the new pair_source, and dpo_qwen.py reweights by kind with no change. The gold-chosen warning at the end of main() should get a sibling line reporting the held-firm share, since a set dominated by them is a different kind of run.

Cost. No extra generate and no extra judge calls — those already ran before the row was dropped. The only new work is two ref_logprob forwards on ~840 rows.

6Choosing the negatives

The negative is the whole design. Three constraints:

  • It must not be one string. 840 copies of a single template teaches the model to unlearn that literal string, not the behaviour. Draw from a pool.
  • It must stay in the model's own register. The pool should be text the policy actually produces, so the pair is about when to say it, not how it is worded.
  • It must not be all repeat-style. Punishing only “say that again” would leave the targeted-question habit untouched; punishing questions indiscriminately would cost R. Mix both.

Both pools come from a single pass over ds before the row loop, keyed by slurp_id — the same utterance's repeat and repair rows already carry exactly the two negatives we want, and they are varied: the repeat targets alone span 90 distinct phrasings across the pairs already built.

# in main(), before the row loop -- nested beside sample_k / ref_logprob,
# which is where a single-caller helper belongs in this repo
by_kind = {"repeat": {}, "repair": {}}   # kind -> slurp_id -> target
for r in ds:
    if r["kind"] in by_kind and r["target"]:
        by_kind[r["kind"]].setdefault(r["slurp_id"], r["target"])
repeat_by_id, repair_by_id = by_kind["repeat"], by_kind["repair"]
rng = random.Random(0)   # re-running the pairs stage must reproduce

def hold_firm_negative(row):
    """A reply that is right on another row of this utterance and wrong here.

    REPEAT_SHARE of them are the generic 'say that again' phrasing, which is
    the single largest leak (8 -> 63 answerable rows); the rest are the
    utterance's own targeted repair question, asking about a slot that on
    THIS row was never masked. Falls back across the two pools, then to the
    global repeat pool, so a missing sibling row never drops a pair."""
    sid = row["slurp_id"]
    want_repeat = rng.random() < REPEAT_SHARE
    first, second = ((repeat_by_id, repair_by_id) if want_repeat
                     else (repair_by_id, repeat_by_id))
    return (first.get(sid) or second.get(sid)
            or rng.choice(list(repeat_by_id.values())))

7Second-order effect on the kind weights

Worth flagging because it is not obvious and it partly works against the fix. dpo_qwen.py's weights are len(prefs) / (n_kinds * n_kind[k]), so growing the answer bucket raises the per-pair weight of the other two:

weight per pairanswerrepairrepeat
now (1117 pairs)2.340.551.35
after (+840 → 1957 pairs)0.650.962.37

Total mass per kind is unchanged by construction — that is the whole point of the scheme — and the real win is that the answer mass now spreads over 999 diverse rows instead of concentrating on 159 hard ones. But each individual repeat pair now carries 2.37, and the repeat kind is where the leaked phrasing comes from. This is why REPEAT_SHARE is tuned against the post-fix weights in §6 rather than the current ones, and it is the reason the “drop the repeat kind” option in §10 stays on the table as a follow-up.

8Run order

The SFT adapter and the eval are unchanged; only stages 3 and 4 of configs/mask-crf.yaml re-run. Rename the outputs so the current v2 sweep is not overwritten — the config header warns about exactly this.

# configs/mask-crf.yaml -- change these three, leave the rest
prefs:        results/mask_prefs_Qwen2.5-Omni-3B-mask-v2-sft-hf.jsonl
dpo_run_name: Qwen2.5-Omni-3B-mask-v2-dpo-hf
tag:          mask-v2-hf

# 1. rebuild the pairs (re-samples K=8 + judges; the expensive stage)
python mask_dpo_data.py --config configs/mask-crf.yaml

# 2. sanity-check the composition BEFORE training -- this is the whole fix
#    expect ~840 held-firm, and the answer bucket near 1000
grep -o '"pair_source": "[a-z-]*"' results/mask_prefs_*-hf.jsonl | sort | uniq -c

# 3. DPO, then eval
python dpo_qwen.py       --config configs/mask-crf.yaml
python mask_eval_qwen.py --config configs/mask-crf.yaml

Stage 1 re-samples from scratch, which is the bulk of the wall clock. If that is worth avoiding, the alternative is to run only the minting half over the rows the current run dropped and concatenate the two JSONLs — but the sampler is not currently resumable, and a clean rebuild keeps every pair drawn from one policy snapshot, which is the property the on-policy design in mask.html §9 exists to protect.

9Risks & falsification checks

Over-correction: R and F fall back. The most likely failure. ~840 pairs saying “do not ask here” could push the model back toward SFT's confident-wrong behaviour on genuinely masked rows.
Check: repair@0 in the eval histogram. SFT 59, DPO 7. If the new run comes back above ~40, REPEAT_SHARE is too low (the targeted-question negatives are teaching “questions are bad” rather than “questions are bad here”) — raise it toward 1.00, which shifts the punishment onto the repeat phrasing alone.
The negatives are off-policy, so the pairs may be too easy to teach anything. The rejected side is dataset text, not a sample; if its reference log-prob is already far below chosen, the pair sits in the saturated tail of logsigmoid and contributes almost no gradient — 840 pairs that look right in the file and do nothing in the run.
Check: the margin and reward_acc the trainer already logs. If reward_acc sits at 1.0 from step 0 with a large positive margin, the held-firm pairs are saturated. The recorded ref_logp_chosen / ref_logp_rejected in the JSONL let you see this before training: histogram their difference for pair_source == "held-firm" and compare against sampled.
Template memorisation. Even a 90-phrasing pool is small next to 840 pairs, and the same strings appear as chosen on repeat rows. The model could learn to down-weight those specific sentences rather than the behaviour, which would look like a fix on C and quietly damage repeat.
Check: repeat@1 in the eval (SFT 361, DPO 393). A collapse here means the pool is being memorised as bad text; if so, the negatives need to be sampled from the policy on the utterance's own repair/repeat audio rather than lifted from targets.
The whole diagnosis could be an artefact of the judge. All numbers here come from one Qwen3.8-27B judge with 0 reported failures, and the C rubric scores a clarifying question on an answer row as 0 by construction.
Check: the 65 regressions are all questions on commands that are demonstrably actionable (§3), and the 8 → 63 repeat-phrasing count is a string match, not a judgement. Both hold without the judge. This risk is low but should be stated in the paper rather than assumed away.

10What was considered and not chosen

Drop the repeat kind from the DPO pair set

Train on answer+repair only (958 → 842 pairs), one filter in dpo_qwen.py, no re-sampling. The repeat pairs bought +32 rows on a kind SFT already had at 90% and are the origin of the leaked phrasing. Cheapest experiment by far (~11 min train + one eval) and it composes cleanly with the chosen fix — §7 is an argument for trying it after. Not chosen first because it treats a symptom: the ~840 unanchored answer rows stay unanchored, so the repair pairs alone can re-create the drift.

Add an NLL anchor on chosen (RPO)

loss += alpha * -log p(chosen)/ntok, alpha ~0.5–1.0, about six lines in compute_loss using logits that are already computed. It attacks Cause 3 directly: DPO sees only a difference, so the NLL term makes the chosen response's absolute likelihood a target too. The standard fix for this drift and it composes with the chosen one. Not chosen first because it does nothing about Cause 1 — it can only anchor rows that are in the pair set, and ~840 answer rows are not.

Evaluate the earlier checkpoints instead

checkpoint-69 / -138 / -207 all exist under checkpoints/Qwen2.5-Omni-3B-mask-v2-dpo/, and the margin grows monotonically, so C very likely degrades along a frontier. Two eval runs, zero training. Worth doing as a free diagnostic — it tells you whether C-vs-R is a smooth trade (pick a point and move on) or a cliff (the pair set is wrong). But it buys a trade-off point rather than removing the trade-off, so it is not a fix.
